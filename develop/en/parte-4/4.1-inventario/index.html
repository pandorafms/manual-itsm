    Inventory¶

    Pandora ITSM's inventory does not fail because of the console: it fails because of the data model. A list of devices can be put together in ten minutes; a useful inventory requires deciding beforehand which object types exist, which fields are shared, who can see what and how objects relate to each other. The rest —views, filters and widgets— comes almost for free.

    This chapter covers the whole inventory: object types, custom and external fields, objects, hierarchy, stock, statuses, tags, ACL, CSV import and remote inventory from Pandora FMS. The Pandora FMS integration is detailed in chapter 11.4; here we explain what the inventory does with it.

    The inventory tells you which objects the organisation has, where they are, who uses them and which contracts, tickets and changes they relate to. It does not discover the network on its own. Objects come in by hand, by CSV or from the Pandora FMS synchronisation.

    Object types¶

    An object type defines the data template for a set of objects. A Computer does not have the same fields as a licence or a contract. The menu is Inventory → Object Types.

    To create a type, click Create, fill in its characteristics and click Create again. To edit it, click its name. The list lets you duplicate a type with all its custom fields through Duplicate.

    The type parameters are:

    Parameter What it is for
    Name Object type name.
    Icon Associated icon; images are uploaded to images/objects/.
    Show in tree view If enabled, the type appears as a root in the tree view.
    Min. stock Minimum stock for the type.
    Max. stock Maximum stock for the type.
    Catalogs to show in overview Catalogs shown as sections in the object overview.
    Description Type description.
    Sync interval How often it synchronises with Pandora FMS: Never, Weekly, Every 15 days, Monthly or First time only.

    Sync interval only appears when Pandora FMS nodes are configured and the type is associated with a Pandora FMS schema. Without the integration, there is nothing to synchronise.

    Custom and global fields¶

    Each type has its own fields. They are managed from Actions → Fields in the type list: create them with Create, edit them by clicking their name and order them with the arrows in the actions column. Deletion lives there too.

    Global fields are the useful exception: they are defined once in Inventory → Object types → Global Fields and added to every type. Each type can hide them or change their order, but the field is the same. Use them for what is always present: serial number, location, purchase date.

    The properties shared by all fields are:

    Property Effect
    Unique Only one object can hold that value; it works as an identifier.
    Inherit The object inherits owner, users and companies from its parent object.
    Show in list The field appears by default in the general list and can be used as a column.
    Prevent updates The field is not updated when remote inventory data arrives.

    The available data types are: numeric, checkbox, text, option list, external field, date, web link, password and value with unit. In the option list, values are separated by commas in Combo values.

    External fields¶

    An external field reads information from an additional database table, created by hand with the DB Manager. It is the way to link the inventory to your own catalogues without turning every value into a static list.

    In a simple field you set two mandatory values: External table name, the exact table name, and Field to be displayed, the column shown. Objects update themselves when the table changes. Primary key, Foreign key and Parent table name are left empty: they belong to composite fields.

    A composite field chains two tables. The parent table has a primary key; the child table has a foreign key pointing to it. When creating the parent field you set the Primary key; when creating the child, the Foreign key and the Parent table name. The result is a drop-down that depends on the previous value: if you clear the parent, the child can be chosen again.

    The classic case is country and city. Create the tables with the DB Manager:

    CREATE TABLE t_country (
    id_country INT PRIMARY KEY,
    name TEXT
);

CREATE TABLE t_city (
    id_city INT,
    name TEXT,
    id_country INT,
    FOREIGN KEY (id_country) REFERENCES t_country(id_country)
);

    Add the values with INSERT, create the Country field on t_country and the City field on t_city with id_city as the primary key, id_country as the foreign key and t_country as the parent table. From then on, any object of the chosen type can select a country and a city. If the field has Show in list, it also appears as a column and as a filter.

    Inventory objects¶

    Objects are created in Inventory → Lists with Create. Before filling in fields, decide who can see them:

    • Owner: owner of the object.
    • Associated companies: associated companies.
    • Associated users: associated users.
    • Public: if enabled, everyone sees it.

    Those four fields are the object's ACL. An object is visible to its owner, to associated users, to users of associated companies and to everyone if it is public. Nobody else sees it.

    An object can have a Parent, which creates a hierarchy, and relationships with other objects. It also stores the type, status, contract, receipt date, issue date, EOL date, an image and a QR code.

    The object view has two columns. On the right are the main data and actions; on the left, the tabs:

    • Custom fields.
    • Tickets: history of associated tickets.
    • Changes: associated changes.
    • Relationships.
    • Tracker: history of changes to the object and its children.
    • Associated users.

    Objects of type Computer add Hardware, Software and Extended Info with the information collected from Pandora FMS.

    Objects can be duplicated from the list with Duplicate; it is the quick way to register ten devices that only differ in the serial number. They can also be reclassified into another type: the system asks how each source field maps to the destination, converts internal identifiers and lets you fill in the new fields by hand. Some fields are discarded; review the result.

    Views, searches and bulk operations¶

    Inventory → Lists offers four ways of looking at the same thing:

    • Overview: landing page with the inventory status and the main types.
    • List: data table with filters, configurable columns and export.
    • Tree: parent-child hierarchy, grouped by type.
    • Stock: stock control, explained below.

    The search filters by free text —description, identifier and custom fields—, by status, by object type and by page size. The result can be exported to CSV.

    In list mode you can select several objects and run bulk operations: delete, change the object type, parent, company, contract, owner or status. Deletion is irreversible; the rest can be undone object by object.

    Stock control¶

    Stock is not kept as a loose number: it is calculated from two pieces. Each type has min_stock and max_stock; each object has a relationship limit (relation_limit, labelled Max relations in the interface).

    • With 0 or empty, the object counts as one unit and allows unlimited relationships.
    • With 1 or more, the object allows at most that number of relationships and appears on the second level of stock control.

    The stock view has two levels. The first shows each type with its minimum, maximum and used stock, a percentage bar and actions to view objects, create a ticket, create a change or schedule a task. The second shows objects with a relationship limit and their usage percentage. If the total drops below the minimum, the warning turns red.

    Statuses and tags¶

    Inventory → Status manages object statuses. Pandora ITSM ships five internal statuses: New, In use, Unused, Issued and Missing. They can be edited, and you can add your own. If a status that was assigned is deleted, the affected objects go back to New.

    Tags (Inventory → Tags) work as in the rest of the console: name, colour and relationship with objects. They are not shown by default in the list; add them as a column or filter by them.

    Inventory ACL¶

    Inventory has its own set of permissions:

    Bit What it allows
    VR View the objects you have access to.
    VW Create, edit and delete objects; includes read access.
    VM Manage the whole inventory: objects, types, statuses, tags and catalogues.

    Read access is not global: the object's visibility applies (public, owner, associated user or associated company). Writing requires VW or VM, and managing types, statuses and tags requires VM. The super administrator bypasses the ACL. The role of the company in the other sections is explained in chapter 2.3.

    Dashboards and widgets¶

    The inventory provides its own dashboard widgets:

    • Inventory by status: percentage by status, filterable by type.
    • Inventory by object type: percentage by type, with multi-selection.
    • Top N stock inventory: the types with the highest usage percentage.
    • Stock relations: global stock and stock per object with a relationship limit.
    • Inventory counter: object count.
    • Inventory type boxes: shortcuts by object type.

    Importing from CSV¶

    Bulk import lives in Inventory → Import CSV. Choose the object type, check the separator —| by default— and download the template with Download sample CSV. The template changes with the type because it includes its custom fields.

    The file must have a header in the first row and at least nine columns in this order:

    Position Column Content
    1 Name Object name. Mandatory.
    2 Owner Owner user. Mandatory and must exist.
    3 Status Status by label or identifier. Mandatory.
    4 Receipt date Receipt date.
    5 Removal date Issue date.
    6 Description Description.
    7 Companies Company identifiers separated by commas.
    8 Associated user User identifiers separated by commas.
    9 Parent Identifier of the parent object, if any.
    10+ Custom fields In the order of the type template.

    Companies and users accept brackets and spaces, but a comma-separated list is the safe option. Custom fields are validated according to their type: numbers, closed lists, dates, external fields and uniqueness. If a row fails, the import reports the line and the reason.

    This format is not what earlier versions of the documentation described: those listed manufacturer, contract, object type or public columns. In the current version the type is chosen in the form and the rest comes from the template. The code is the reference.

    Remote inventory from Pandora FMS¶

    Remote inventory does not receive XML files from EndPoints directly: it synchronises from Pandora FMS. The Pandora FMS server collects the information with its EndPoints and Pandora ITSM reads it through the configured node, creating or updating the objects. Sending inventory directly from an EndPoint to Pandora ITSM no longer exists.

    The destination configuration is in Setup → Pandora FMS Inventory, section Remote Inventory:

    • Default owner: owner of the new objects. It is mandatory.
    • Associated companies: default companies.
    • Associated users: default users.

    Those values fill the objects created by the synchronisation and therefore decide their visibility. The Pandora FMS node, its credentials and its scope are configured in the integration; chapter 11.4 covers the full procedure.

    Synchronisation is not immediate: each object type sets its pace with Sync interval (Never, Weekly, Every 15 days, Monthly or First time only). The type must be associated with the Pandora FMS schema for the option to appear.

    The inventory cron is what makes this work. It runs include/inventory_cron.php and must be in crontab, usually every five minutes:

    php /var/www/html/pandoraitsm/include/inventory_cron.php

    On each run it records the inventory_crontask mark, synchronises the inventory from the Pandora FMS nodes respecting each type's interval, expires overdue schedules and removes Missing objects that no longer have a parent.

    EndPoints are installed and configured in Pandora FMS, not in Pandora ITSM: they feed the monitoring server. ITSM only consumes the result through the node. Hardware, software and extended information for Computer objects arrive that way and are linked through id_pandora.

    Good practices¶

    • Define few object types and fields with judgement; every extra field is paid for on every registration, filter and import.
    • Use global fields for what all types share and own fields for what is specific.
    • Model the hierarchy before importing: changing parents later is more expensive.
    • Review Min. stock and Max. relations before stock starts lying to you.
    • Respect the ACL from the start: owner, companies, users and Public decide who sees the object.
    • Do not turn the inventory into network discovery: if the data is not in Pandora FMS or the CSV, it does not appear.
