    Versions and support lifecycle¶

    Pandora ITSM is not updated for the sake of updating. Each release has a goal: an LTS prioritises keeping the system standing; an FR prioritises getting what is new sooner. Choosing the wrong channel does not break the product on day one; it breaks the team's peace of mind when the first incident arrives.

    The point of this chapter is simple: do not look for the highest version; look for the one you can defend. The latest LTS is the usual reference for production, but a well-supported earlier version is still better than a badly tested latest one.

    How versions are read¶

    Each installation is described by four pieces of data:

    Data Example What it is
    Version 5.0.110 Product version
    OUM 110 Offline Update Manager release
    MR 110 Database migration level
    Package 5.0.110-261001 Package and build date

    The version is the product version. The OUM is the release package published through the Offline Update Manager. The MR is the database migration level. The package adds the build date; it is not a different version.

    Since 105, the OUM matches the version: 5.0.105 is OUM 105, 5.0.106 is OUM 106 and so on up to 110. The MR does not always follow: 5.0.105 was OUM 105 and MR 98; 5.0.106 was already MR 106. That is why the three are read together in About ITSM; none replaces the others.

    An example: an installation with version 5.0.110, OUM 110 and MR 110 is on release 110 and has the database up to date. If the MR lags behind, the code may be new while the schema is old.

    LTS version¶

    LTS stands for Long Term Support. It is the reference version for production: it is published less often than FRs, it is validated more and it is maintained with security patches and critical fixes.

    What you need to keep clear:

    • An LTS does not receive the new features from FRs. It receives fixes, not novelties.
    • LTS patches come out as needed, not on a fixed cadence.
    • The end-of-support date shown in About ITSM is the licence date, not the version date. It tells you whether you are covered, not when to update.
    • The real limit is usually the operating system: if the vendor stops supporting EL9 or Ubuntu 22.04, the longest-lived LTS loses its foundation.

    Unless there is a specific reason otherwise, production runs on LTS. And to stay on track without thinking about it, Warp Update has the Limit to LTS updates option, which skips intermediate versions.

    Feature Release (FR) version¶

    FR stands for Feature Release. It is the version that brings new features, improvements and fixes on a more frequent cadence than the LTS.

    It makes sense in three cases:

    • You need a specific feature before it reaches the LTS.
    • You have a pilot environment where you can test without putting the service at risk.
    • The team accepts that each release must be reviewed, tested and applied.

    Keeping a critical environment on FR without room for testing is not a good idea. An FR may also receive patches, but changes normally arrive with the next FR. Novelty is tested where you can go back.

    LTS patches¶

    An LTS does not stand still: it receives patches. An LTS patch fixes a vulnerability, a relevant incident or a critical failure without changing the family or bringing new features.

    Patches are identified by the version and the release number published by the vendor; the source is the official updates page and the notes for each OUM. Do not invent your own naming or mix an FR patch with an LTS.

    They are applied with Warp Update, just like a full release. The procedure is in 1.2; here only the criterion matters: if it is an LTS patch, it goes to the LTS; if it is a new feature, it goes to the FR.

    Support lifecycle¶

    The reference for production is the latest LTS or, with a justified reason, the previous one that is still supported. There is no promise of indefinite support for an old LTS: when a new one is published, the previous one enters the planning zone.

    Two dates are easy to confuse and should be kept apart:

    • Licence end of support: shown in About ITSM. It is tied to payment and the contract.
    • Version end of life: marked by the release cycle and, in practice, by the operating system.

    Before stretching an LTS, look at the operating system calendar and the support contract. Licensing details are in 1.4; here it is enough to know that the licence date is not the version date.

    Compatibility¶

    The reference version, 5.0.110, lives in this window:

    Component Versions
    RHEL, Rocky Linux or AlmaLinux EL 9 and EL 10
    Ubuntu Server 22.04 and 24.04
    PHP 8.2 and 8.4
    MySQL or Percona 8.0 and 8.4, with EL10 limited to 8.4

    The full matrix and installation are in 1.1. If your current version does not meet this window, the problem is not solved by updating the product: it is solved by updating the platform.

    How to choose¶

    For production, the rule is boring and it works:

    1. Check the latest published LTS and its notes.
    2. Confirm that the operating system, PHP and MySQL are still supported.
    3. If you need a feature that only exists in FR, test it in a pilot.
    4. Update to the next release or the latest one, not to an invented combination.
    5. Verify version, MR, services, cron and logs.

    If the FR solves a real problem, bring the update forward, but do it with a backup and a maintenance window. Stability is not negotiated on what keeps the service running.

    Where to look¶

    • About ITSM: version, MR and package of the installation.
    • Warp journal: history of applied updates.
    • Official updates page: published releases and notes.
    • OUM notes: what each release brings and fixes.
    • Warp Update: LTS, non-consecutive patches and proxy options.

    Updating¶

    The procedure is in 1.2. Here the criterion remains: choose the channel, check compatibility, make a backup and update. Then check the MR and the journal.

    Next steps¶

    • Review the licence and support contract (1.4).
    • Check the compatibility matrix before the next update.
    • Schedule backups and monitoring (Part 12).
    • Note the version, OUM and MR in the journal.
