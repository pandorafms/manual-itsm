    Tickets and incidents¶

    A ticket is the smallest unit of support work: someone has a problem, someone else takes ownership, and the system records what happened, when, and with how much effort. Everything else —emails, calls, messages— is a way of reaching the ticket, not a replacement for it.

    The temptation to treat the mailbox as the support queue is strong and always ends the same way: requests without an owner, answers that exist only in one person's inbox, and statistics nobody dares to look at. Pandora ITSM exists so that every request has a number, a status and a responsible person.

    What a ticket is¶

    A ticket can be an incident, a request, a question or a small change. What defines it is not the subject but the contract:

    • It has a creator who describes the problem.
    • It has an owner who commits to solving it.
    • It has a status that says where it stands.
    • It has a group that determines who can see and work on it.
    • It has a history of comments, files and time.

    Without an owner, the ticket is a note in the air. Without a status, nobody knows whether the problem is still alive. Without a group, visibility becomes a lottery.

    Who is who¶

    More people take part in a ticket than it seems. Confusing the roles is an endless source of arguments:

    Role What it does
    Creator Finds the problem and describes it. Keeps visibility even if the ticket changes group.
    Owner Is responsible for solving it. It can be a user or a team, but only one at a time.
    Editor Enters the ticket into the system, even if they are neither its creator nor its solver.
    Contributor Provides information without being creator or owner.
    Associated user Has taken part at some point and receives notifications.
    Support team Groups several users and allows collaborative work or automatic distribution.

    The Contacts tab shows the full list of participants and their role. Edit permissions allow you to create tickets; seeing someone else's ticket requires visibility over their group.

    How a ticket is created¶

    Manual creation is still the standard: Support → Create new ticket. The form shows the common fields and the custom fields of the selected type.

    In Setup → Setup → Issue setup → Ticket submission settings you can choose the creation mode:

    • Manual: all available fields. It is always accessible.
    • Simplified: only the mandatory fields: title, type, criticality, group, description, mandatory custom fields and files.
    • Smart: the user writes a question and the system searches the knowledge base before opening the ticket. If the answer solves the question, it can be marked as solved; if not, the ticket is created with the context. It needs an OpenAI API Key and a well-tuned System prompt.

    Smart mode is not a fortune teller: if the knowledge base is empty or the prompt is too generic, it will return beautiful but useless answers. It is a way to avoid repeated tickets, not an excuse to stop documenting.

    Tickets can also be created by email. That path has its own rules and is explained in 3.4 Email and support.

    Teams and availability¶

    A support team lets several people work on the same queue. It is created in People → Teams, needs the support bit enabled and is configured in Support → Teams.

    Working modes:

    • Collaborative work: the ticket is assigned to the team and all its members can see and work on it.
    • Round Robin: rotating distribution among members.
    • Load Balanced: assignment to the member with the least active workload.
    • Availability: only assigns to users with an active status in the Timetracker.
    • Fallback: if nobody is available, the ticket goes to a specific user. If none is configured, it stays assigned to the team.

    Automatic distribution is convenient until someone forgets to activate their shift. If the Timetracker does not reflect reality, the algorithm will hand tickets to people who have been offline for two hours. Automation does not fix poor availability management.

    Ticket anatomy¶

    The main fields are title, description, criticality, group, type and status. The description supports rich HTML, links and images, and the ticket can carry attached files.

    Advanced parameters contains the fields that are not always visible:

    • Parent ticket: parent-child relationship between tickets.
    • Project Task: link to a project task.
    • Change: link to a change.
    • Inventory objects: traceability of the affected elements.
    • Emails in copy: third parties who receive a copy without access to the application.

    The Editor and Creator group are fixed for auditing: they cannot be changed and are used as filters in workflow rules.

    Work units¶

    The conversation of a ticket is built with work units (WU). Each one can include:

    • Time dedicated (hours): time spent.
    • Private work unit: visible only to administrators and to its author.
    • Internal work unit: hidden from the ticket creator.
    • Add to project's cost: charges the cost to the project.
    • Work unit shared with: mentions another user, who receives a notice.
    • Description: rich text, links and images.

    Every WU, file or status change generates notifications to the associated users. That is the difference between a living ticket and a document someone opened once.

    Types and custom fields¶

    In Support → Tickets types → View tickets types you define ticket types. Each type can have its own fields: single-line text, long text, date, numeric, true/false, Combo and Linked.

    Details worth learning before they bite:

    • Global field creates a field common to all types.
    • Show in the list of tickets displays it in the list.
    • Required makes it mandatory.
    • In a mandatory Combo, the option string must start with a comma so the first option stays empty.
    • Linked fields chain a parent field to a child field. For example, Peripherals with Keyboard,Mouse and a second field showing Keyboard|USB, Keyboard|Bluetooth, Mouse|USB.

    A ticket type with twenty mandatory fields does not improve information: it improves the speed at which the user abandons the form. Add fields when they will really be used in filters, reports or workflows.

    Statistics and work orders¶

    The ticket statistics tab summarises times, work units, activity by user, status, group, company and SLA. It is useful for answering concrete questions, not for decorating a meeting.

    Work orders are created from templates in Support → Tickets types → Work order templates. Templates use macros such as _incident_id_, _incident_title_, _owner_, _author_, _status_, _resolution_, _time_used_ or custom fields. The work order is generated as a PDF and can be validated by uploading the version signed by the customer.

    Bulk operations and import¶

    In Support → All tickets you can select several tickets and bulk-change status, priority, resolution, tag, group, owner or parent. The interface is shown to everyone, but every operation checks permissions. Bulk deletion exists; treat it as a demolition tool.

    CSV import is in Support → Import tickets from csv. The column order is fixed: start, close, title, description, user, status, priority, group, update, creator, task, resolution, epilogue, parent, SLA disabled, SLA, type, score, copies, editor, creator group, last status, closed by, extra data, blocked, old statuses and resolutions, rating and comment. Custom fields go at the end, in the defined order, and must already exist.

    The life cycle of these tickets is detailed in 3.2 Workflow and statuses; service metrics are in 3.3 SLA, escalation and quality.
