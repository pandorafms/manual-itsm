    Tickets et incidents¶

    Un ticket est la plus petite unité de travail du support : quelqu'un a un problème, une autre personne en prend la responsabilité, et le système garde trace de ce qui s'est passé, quand et avec quel effort. Le reste —courriels, appels, messages— sont des moyens d'arriver au ticket, pas des substituts.

    La tentation de traiter la boîte aux lettres comme la file d'attente du support est grande et finit toujours de la même façon : des demandes sans responsable, des réponses qui n'existent que dans la boîte d'une personne et des statistiques que personne n'ose regarder. Pandora ITSM existe pour que chaque demande ait un numéro, un état et un responsable.

    Qu'est-ce qu'un ticket¶

    Un ticket peut être un incident, une demande, une question ou un petit changement. Ce qui le définit n'est pas le sujet, mais le contrat :

    • Il a un créateur qui décrit le problème.
    • Il a un propriétaire qui s'engage à le résoudre.
    • Il a un état qui indique où il en est.
    • Il a un groupe qui détermine qui peut le voir et le traiter.
    • Il a un historique de commentaires, de fichiers et de temps.

    Sans propriétaire, le ticket est une note dans le vide. Sans état, impossible de savoir si le problème est toujours vivant. Sans groupe, la visibilité devient une loterie.

    Qui est qui¶

    Plus de personnes que prévu interviennent dans un ticket. Confondre les rôles est une source inépuisable de discussions :

    Rôle Ce qu'il fait
    Créateur Détecte le problème et le décrit. Conserve la visibilité même si le ticket change de groupe.
    Propriétaire Est chargé de le résoudre. Peut être un utilisateur ou une équipe, mais un seul à la fois.
    Éditeur Saisit le ticket dans le système, même s'il n'est ni le créateur ni celui qui le résout.
    Contributeur Apporte des informations sans être créateur ni propriétaire.
    Utilisateur associé A participé à un moment donné et reçoit les notifications.
    Équipe de support Regroupe plusieurs utilisateurs et permet le travail collaboratif ou la répartition automatique.

    L'onglet Contacts affiche la liste complète des participants et leur rôle. Les permissions d'édition permettent de créer des tickets ; pour voir le ticket d'une autre personne, il faut avoir la visibilité sur son groupe.

    Comment créer un ticket¶

    La création manuelle reste la norme : Support → Create new ticket. Le formulaire affiche les champs communs et les champs personnalisés du type choisi.

    Dans Setup → Setup → Issue setup → Ticket submission settings, on peut choisir le mode de création :

    • Manual : tous les champs disponibles. Toujours accessible.
    • Simplified : uniquement les champs obligatoires : titre, type, criticité, groupe, description, champs personnalisés obligatoires et fichiers.
    • Smart : l'utilisateur écrit sa question et le système cherche des réponses dans la base de connaissance avant d'ouvrir le ticket. Si la réponse résout la question, elle peut être marquée comme résolue ; sinon, le ticket est créé avec le contexte. Il faut une API Key OpenAI et un System prompt bien réglé.

    Le mode Smart n'est pas un devin : si la base de connaissance est vide ou si le prompt est trop générique, il renverra de belles réponses inutiles. C'est une aide pour éviter les tickets répétés, pas une excuse pour arrêter de documenter.

    Les tickets peuvent aussi être créés par courriel. Ce chemin a ses propres règles et est expliqué dans 3.4 Courriel et support.

    Équipes et disponibilité¶

    Une équipe de support permet à plusieurs personnes de travailler sur la même file. Elle se crée dans People → Teams, nécessite le bit de support activé et se configure dans Support → Teams.

    Modes de travail :

    • Travail collaboratif : le ticket est affecté à l'équipe et tous ses membres peuvent le voir et le traiter.
    • Round Robin : répartition tournante entre les membres.
    • Load Balanced : affectation au membre ayant la charge active la plus faible.
    • Disponibilité : affectation uniquement aux utilisateurs avec un état actif dans le Timetracker.
    • Fallback : si personne n'est disponible, le ticket va à un utilisateur précis. Sans configuration, il reste affecté à l'équipe.

    La répartition automatique est pratique jusqu'à ce que quelqu'un oublie d'activer sa journée. Si le Timetracker ne reflète pas la réalité, l'algorithme confiera des tickets à des personnes déconnectées depuis deux heures. L'automatisation ne corrige pas une mauvaise gestion de la disponibilité.

    Anatomie du ticket¶

    Les champs principaux sont le titre, la description, la criticité, le groupe, le type et l'état. La description accepte du HTML enrichi, des liens et des images, et le ticket peut contenir des fichiers joints.

    Advanced parameters contient les champs qui ne sont pas toujours visibles :

    • Parent ticket : relation parent-enfant entre tickets.
    • Project Task : lien avec une tâche de projet.
    • Change : lien avec un changement.
    • Inventory objects : traçabilité des éléments concernés.
    • Emails in copy : tiers qui reçoivent une copie sans accès à l'application.

    L'Editor et le Creator group sont fixes pour l'audit : ils ne changent pas et servent de filtres dans les règles de workflow.

    Unités de travail¶

    La conversation d'un ticket se construit avec des unités de travail (WU). Chacune peut inclure :

    • Time dedicated (hours) : temps passé.
    • Unité de travail privée : visible uniquement par les administrateurs et son auteur.
    • Unité de travail interne : masquée au créateur du ticket.
    • Add to project's cost : impute le coût au projet.
    • Partagée avec : mentionne un autre utilisateur, qui reçoit un avis.
    • Description : texte enrichi, liens et images.

    Chaque WU, fichier ou changement d'état génère des notifications aux utilisateurs associés. C'est la différence entre un ticket vivant et un document que quelqu'un a ouvert une fois.

    Types et champs personnalisés¶

    Dans Support → Tickets types → View tickets types, on définit les types de ticket. Chaque type peut avoir ses propres champs : texte sur une ligne, texte long, date, numérique, vrai/faux, Combo et Linked.

    Détails qu'il vaut mieux connaître avant de se faire surprendre :

    • Global field crée un champ commun à tous les types.
    • Show in the list of tickets l'affiche dans la liste.
    • Required le rend obligatoire.
    • Dans un Combo obligatoire, la chaîne d'options doit commencer par une virgule pour laisser la première option vide.
    • Les champs Linked enchaînent un champ parent et un champ enfant. Par exemple, Peripherals avec Keyboard,Mouse et un second champ affichant Keyboard|USB, Keyboard|Bluetooth, Mouse|USB.

    Un type de ticket avec vingt champs obligatoires n'améliore pas l'information : il améliore la vitesse à laquelle l'utilisateur abandonne le formulaire. Ajoutez des champs quand ils serviront vraiment aux filtres, aux rapports ou aux workflows.

    Statistiques et ordres de travail¶

    L'onglet des statistiques du ticket résume les temps, les unités de travail, l'activité par utilisateur, l'état, le groupe, l'entreprise et le SLA. Il est utile pour répondre à des questions concrètes, pas pour décorer une réunion.

    Les ordres de travail (Work order) se créent à partir de modèles dans Support → Tickets types → Work order templates. Les modèles utilisent des macros comme _incident_id_, _incident_title_, _owner_, _author_, _status_, _resolution_, _time_used_ ou les champs personnalisés. L'ordre est généré en PDF et peut être validé en téléversant la version signée par le client.

    Opérations massives et importation¶

    Dans Support → All tickets, on peut sélectionner plusieurs tickets et modifier en masse l'état, la priorité, la résolution, l'étiquette, le groupe, le propriétaire ou le parent. L'interface est visible par tous, mais chaque opération vérifie les permissions. La suppression massive existe ; traitez-la comme un outil de démolition.

    L'importation CSV se trouve dans Support → Import tickets from csv. L'ordre des colonnes est fixe : début, clôture, titre, description, utilisateur, état, priorité, groupe, mise à jour, créateur, tâche, résolution, épilogue, parent, SLA désactivé, SLA, type, score, copies, éditeur, groupe créateur, dernier état, clos par, données extra, bloqué, anciens états et résolutions, évaluation et commentaire. Les champs personnalisés vont à la fin, dans l'ordre défini, et doivent déjà exister.

    Le cycle de vie de ces tickets est détaillé dans 3.2 Flux de travail et états ; les métriques de service dans 3.3 SLA, escalade et qualité.
