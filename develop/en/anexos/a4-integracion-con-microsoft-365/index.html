    Microsoft 365 integration¶

    Microsoft 365 requires OAuth 2.0 for Pandora ITSM to send and receive email with a corporate account. The integration is configured in two places: an Azure AD application and the SMTP/POP/IMAP settings in Pandora ITSM. Functional email configuration is in 3.4 Email and support; this annex explains the Azure AD registration step by step.

    Create an Azure AD application¶

    The application represents Pandora ITSM inside Microsoft 365. It is registered once and reused for sending and receiving.

    Enter the portal¶

    1. Go to https://portal.azure.com/.
    2. Search for Azure Active Directory.
    3. In the side menu, select App registrations.

    Register a new application¶

    1. Click New registration.
    2. Fill in Name with a descriptive name, for example PANDORA.
    3. Choose Supported account types for your organisation. For a single organisation, use Accounts in this organizational directory only.
    4. In Redirect URI (optional) choose Web and enter a sample URL such as http://localhost/pandora.
    5. Click Register.

    Get the identifiers¶

    On the application home page you will see:

    • Application (client) ID: this is Pandora ITSM's Client ID.
    • Directory (tenant) ID: this is the Tenant ID.

    Copy both values. They are public, but they must match the registered application exactly.

    Create a secret¶

    1. In the side menu, open Certificates & secrets.
    2. Under Client secrets, click + New client secret.
    3. Add a description and a duration, for example 6 or 12 months.
    4. Click Add.
    5. Copy the Value immediately: it is shown only once. That is the Client Secret.

    An expired secret does not send a polite email: it simply stops authenticating. Note the expiry date and renew it as part of maintenance.

    Configure redirect URIs¶

    1. Open Authentication.
    2. Under Platform configurations, select Add a platform → Web.
    3. In Redirect URIs, add every valid URL where the application will receive the token. For example:
    http://localhost/pandora
http://localhost/pandoraitsm/godmode/godmode/setup/setup_mail

    In production use the real Pandora ITSM URL, always over HTTPS. A localhost URL is only for testing.

    Connecting with a non-administrator user¶

    If the application will not use a global administrator, review permissions and user consent.

    API permissions¶

    1. In Azure Portal → Azure Active Directory → App registrations, select the application.
    2. Open API permissions.
    3. Check that the Microsoft Graph permissions needed for email are present: email, Mail.Read, Mail.ReadBasic, Mail.ReadWrite, Mail.Send, MailboxSettings.Read, offline_access and User.Read.

    User consent¶

    1. Go to Azure AD → Enterprise applications → User settings.
    2. Open Consent and permissions → User consent settings.
    3. Allow user consent for applications from verified publishers or for the low-impact permissions the application needs.

    If the organisation requires administrator consent, an administrator must approve it. Without that consent, the user cannot authorise the application.

    Secret and Pandora ITSM configuration¶

    1. Generate a new Client Secret if you changed permissions.
    2. Copy the Value.
    3. Paste it into the POP/IMAP Secret field in Pandora ITSM.
    4. Repeat the process if you change permissions again: the previous secret may stop working.

    In Pandora ITSM, sending and receiving with Microsoft OAuth 2.0 requires Client ID, Tenant ID and Secret, plus clicking Connect to Microsoft and accepting the permissions.

    Checks¶

    • The application appears under App registrations.
    • Client ID and Tenant ID are copied without spaces.
    • The Client Secret is valid and stored.
    • Redirect URIs include the real Pandora ITSM URL.
    • Microsoft Graph permissions are granted.
    • User or administrator consent is resolved.
    • Pandora ITSM can connect and send a test email.

    Best practices¶

    • Use one application per environment: development, testing and production.
    • Document the secret expiry date.
    • Do not share the secret by email or store it in the repository.
    • Use HTTPS in production.
    • Review permissions after every Azure AD change.
    • If something stops working, check the secret and consent first.
