    Updating¶

    Updating Pandora ITSM is not about pressing a button and keeping your fingers crossed. It is a controlled-risk operation: there is data, there are users and there is a version that works. The difference between a boring update and an afternoon of incidents is almost always in what you do before, not in what you press afterwards.

    The point of this chapter is simple: if you do not have a backup, you do not have an update; you have a bet. With a backup, a maintenance window and a clear target version, Warp update does almost everything. Without them, the prettiest button in the world will not save you.

    Before updating¶

    Before touching anything, prepare the ground:

    • Full backup: database, /var/www/html/pandoraitsm and attachments. A database dump alone is not enough; files count too.
    • Maintenance window: tell users and leave time to check the console afterwards.
    • Current and target version: write down the version, MR and package you have. You will find them in About ITSM.
    • Access to the update repository: online updates require registration; offline updates use a temporary code.
    • Disk space and memory: leave room to download, unpack and apply.
    • Compatibility: check that PHP and MySQL/Percona for the target version are still within the supported window.
    • Update path: Warp update online, Warp update offline or the legacy tarball.
    • Plan B: if something fails, do you restore the backup? How long does it take? Who do you tell?

    Do not skip versions without confirming the path first. A bad jump is not fixed with another jump; it is fixed by restoring the backup.

    If the problem is that your licence does not allow updates, this is not the chapter that solves it: see the licensing chapter (1.4).

    How it is updated¶

    There are two interfaces and three real paths:

    Path When to use it Needs Internet
    Warp update online Installation with Internet access and registration Yes
    Warp update offline Isolated or restricted servers No
    Legacy tarball Only if support confirms it is still valid No

    Warp update is the recommended path. The tarball is kept as a legacy option for very specific cases, but it is not the path I would choose for 5.0.110 without asking first.

    Online web update¶

    Open Warp update → Update online.

    The first time, you must register the installation with an email address. The server returns a permanent UID (pandora_uid) that is stored for future updates. Without registration, the online update does not start: the code says so clearly with "Update online requires registration".

    Once registered, the screen offers two buttons:

    • Update to next version: applies the next available version.
    • Update to latest version: jumps to the latest published version.

    If you are already on the latest version, neither button will be enabled. That is not a failure: there is nothing to install.

    Before applying, review the summary of changes and fixes. The download may take a while; do not close the tab or walk away while the process writes files. When it finishes, check the system status and confirm the version in About ITSM.

    Offline web update¶

    Open Warp update → Update offline.

    This path is for environments without Internet access or for installations that, for security reasons, must not talk directly to the repository. Applying offline patches can leave the console unusable; a full backup is not a suggestion, it is the requirement.

    If you have not registered the installation, request a temporary code to access the repository. The flow is:

    1. Enter the email and click Register.
    2. Copy the code and open the link that appears.
    3. Download the .itsm files for the version you are going to apply.
    4. Go back to Update offline and upload each file with BROWSE IT.
    5. Wait for the analysis and apply the update with the green button.

    Only .itsm files are uploaded through this screen; server packages do not go through it.

    The files must fit within the PHP limits:

    post_max_size
upload_max_filesize
memory_limit

    The updater warns if memory_limit is below 800M. On EL it is usually in /etc/php.ini; on Ubuntu, in /etc/php/8.2/fpm/php.ini or /etc/php/8.4/fpm/php.ini, depending on the installed version. If the file does not upload, the problem is almost never the file: it is the limit.

    Legacy tarball update¶

    The tarball is downloaded to /tmp, unpacked and the update script is run as root:

    cd /tmp
tar xzf <name_packet>.tar.gz
cd integria_enterprise
./integria_update -p /var/www/html/pandoraitsm

    The script copies the code, fixes permissions, removes install.php and protects config.php. It is an old tool: it declares version 3.0 and only covers a database migration from 3.0 to 3.1. For 5.0.110, do not use it on your own; confirm with support first that it is still the correct procedure.

    If you use it anyway, make the backup first and then check the version, MR, services and logs. A badly applied tarball shows up late.

    When it finishes, apply the pending database MRs:

    cd /var/www/html/pandoraitsm
php godmode/um_client/updateMR.php

    The script prints the current MR and applies the pending ones. If you skip it, the code may be updated while the database stays behind.

    Warp Update settings¶

    On the Warp update screen you can adjust the connection to the repository:

    Option Purpose
    Warp Update URL Address of the update server
    Use secured Warp Update Forces TLS on the connection
    Proxy server / port / user / password Outbound access through a proxy
    Allow no-consecutive patches Allows non-consecutive updates
    Limit to LTS updates Restricts updates to LTS versions

    Contact support before changing the URL, TLS or proxy. These options are not decoration: if you get them wrong, the console stops seeing the repository and it looks as if the product is broken.

    About Allow no-consecutive patches: in the reference screenshot it is disabled, which is the recommended option. Do not enable it without confirming the behaviour of your version. Limit to LTS updates is enabled by default; if you need a current release, you will have to disable it deliberately.

    Warp journal¶

    Warp update → Warp journal shows the history of applied updates. Each row stores:

    • Version.
    • Type.
    • Origin: online or offline.
    • User.
    • Date.

    The data lives in the tupdate_journal table and can be filtered by keyword. In an audit, this journal is worth more than any email saying "I think I updated it in March".

    After updating¶

    When it finishes, log in again. Then check, in this order:

    1. About ITSM: version, MR and package. They must have changed.
    2. Services: Apache, PHP-FPM and MySQL/Percona running.
    3. Cron: integria_cron.php, crm_cron.php and campaign_cron.php still in /etc/crontab.
    4. Logs: pandora_itsm.log and /var/log/php-fpm/www-error.log.
    5. Functional test: log in, open a ticket, check inventory, enter CRM and run a test campaign.
    6. Warp journal: the update appears with the correct version.

    If something fails, do not improvise on a half-updated installation. Restore the backup, go back to the previous version and open an issue with the logs. A system restored in time is better than one that is "almost updated" for a week.

    Common problems¶

    Symptom Likely cause Check
    No update is offered No registration, no connection or LTS active Check pandora_uid, the network and Limit to LTS updates
    Memory error when applying memory_limit too low Raise it to 800M or more
    The offline file does not upload Extension, size or PHP limits Check .itsm, post_max_size and upload_max_filesize
    The console is unusable after a patch Incomplete or incompatible patch Restore the backup and check the log
    MR does not change Pending MR process Check updateMR.php and the journal
    Services do not start Dependencies or configuration Check Apache, PHP-FPM, MySQL and their logs
    Cron has disappeared Update that rewrites /etc/crontab Add the three entries again
    Version does not change in About ITSM Update not applied or cache Check the journal and log in again

    Next steps¶

    With the update closed:

    • Review the versions and support lifecycle (1.3).
    • Review licensing if the update was limited by licence (1.4).
    • Schedule backups and monitoring (Part 12).
    • Note the applied version and date in the journal.
    • Plan the next update before the calendar catches you.
