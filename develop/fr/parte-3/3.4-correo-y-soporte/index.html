    Courriel et support¶

    Le courriel est la porte d'entrée la plus pratique pour l'utilisateur et la plus facile à casser pour l'administrateur. Dans Pandora ITSM, il ne suffit pas de configurer un serveur SMTP : il faut décider quelles boîtes sont lues, quels expéditeurs sont acceptés et ce qui se passe quand un message ne correspond à aucune file.

    La règle d'or est simple : si un courriel ne correspond pas à une file de groupe, il n'est pas traité. Il n'y a pas de boîte de secours ni de message d'excuse. Le message reste où il est, en attendant que quelqu'un le lise à la main.

    Le ticket résultant suit les règles de 3.1 Tickets et incidents et 3.2 Flux de travail et états.

    Deux adresses qui ne sont pas la même¶

    La configuration courriel de chaque groupe contient deux champs souvent confondus :

    • Email destination : adresses ou alias de la boîte que Pandora ITSM lit pour créer ou mettre à jour des tickets. Accepte plusieurs adresses et expressions régulières, une par ligne.
    • Email origin : filtre des expéditeurs valides. Seuls les courriels qui correspondent à ce champ sont acceptés pour créer ou mettre à jour des tickets. Accepte aussi plusieurs adresses et expressions régulières.

    Le premier dit « de quelle boîte on parle » ; le second, « qui a le droit d'y écrire ». Si Email origin est vide, tout expéditeur est accepté. Si vous les mélangez, vous finirez avec des tickets créés par n'importe qui ou des courriels légitimes ignorés.

    Configuration du courriel¶

    La configuration générale se trouve dans Setup → Setup → Email. Elle comporte deux moitiés :

    Envoi (SMTP)¶

    • System mail from address : expéditeur des notifications.
    • Encryption : aucune, SSL/TLS, SSLv2, SSLv3, STARTTLS ou Microsoft OAuth 2.0.
    • SMTP Host, SMTP Port, SMTP User et SMTP Password.
    • User ID, Client ID, Tenant ID et Secret pour OAuth.
    • SMTP Queue retries, Max pending mail et Max. emails sent per execution pour contrôler la file.

    Le bouton Test vérifie la connexion. Un « test réussi » prouve seulement que le serveur répond ; pas que le courriel arrive dans la boîte de destination.

    Réception (POP/IMAP)¶

    • Encryption, POP/IMAP Host, POP/IMAP Port, POP/IMAP User et POP/IMAP Password.
    • User ID, Client ID, Tenant ID et Secret pour OAuth.
    • Select IMAP or POP : IMAP est généralement le choix sensé ; POP a tendance à déplacer ou supprimer les messages et complique la traçabilité.
    • Message delimiter : indique où couper le fil de réponses.
    • Compatibility : Gmail, Microsoft 365, Outlook, Dreamhost ou autres.

    Si le serveur exige OAuth, il faut connecter l'application et renouveler le secret à son expiration. Un secret expiré n'envoie pas de courriel poli : il cesse simplement de recevoir.

    File de courriel d'un groupe¶

    La configuration du groupe définit ce qui arrive aux messages de sa file :

    • Email destination et Email origin.
    • Autocreate users : crée l'utilisateur si l'expéditeur n'existe pas.
    • Grant access to users : lui donne accès à l'application.
    • Send welcome email et Welcome email : message de bienvenue, avec la macro _password_ si le mot de passe est envoyé.
    • Default status, User type, Default company, Default user's profile et Default ticket type.

    La combinaison de Autocreate users et Grant access to users est pratique et dangereuse à la fois : toute personne qui écrit à la boîte peut devenir utilisateur. Ne l'activez que si le filtre d'origine et le périmètre réseau le justifient.

    Que se passe-t-il à l'arrivée d'un courriel¶

    1. Pandora ITSM lit la boîte configurée.
    2. Il cherche une file de groupe dont Email destination correspond à l'adresse de destination.
    3. Il vérifie que l'expéditeur correspond à Email origin.
    4. Sans correspondance, le courriel n'est pas traité.
    5. Avec correspondance, il cherche un ticket existant par sujet ou en-têtes.
    6. S'il n'en existe pas, il crée un nouveau ticket.
    7. S'il en existe un, il ajoute une unité de travail, met à jour le ticket et enregistre le corps du courriel comme commentaire.

    Lors de la création, le ticket prend ces valeurs :

    • Créateur : utilisateur associé à l'adresse from, s'il existe ou si l'autocréation est active.
    • Éditeur : le même utilisateur from.
    • Groupe : celui de la file.
    • Propriétaire : l'utilisateur par défaut du groupe, s'il est défini.
    • Titre : le sujet.
    • Description : le corps.
    • Notifications : les adresses TO et CC autres que l'adresse de la file.
    • Pièces jointes : les fichiers du message.

    Mettre à jour un ticket par courriel¶

    Certains champs peuvent être modifiés avec un bloc de texte dans le corps du message :

    [INCIDENT]
GROUP: Support
ASSIGNED_TO: operator
PRIORITY: 3
STATUS: Assigned
RESOLUTION: Invalid
[INCIDENT]

    Champs acceptés :

    Champ Valeur
    GROUP Nom du groupe.
    ASSIGNED_TO Identifiant de connexion du propriétaire.
    PRIORITY Numéro de 0 (plus basse) à 5 (plus haute).
    STATUS Nom de l'état.
    RESOLUTION Nom de la résolution.

    Si la syntaxe n'est pas exacte, les changements ne s'appliquent pas et le texte finit en commentaire. Pandora ITSM ne devine pas les intentions ; si vous vouliez changer l'état et avez écrit STATUS : Assigned, vous obtiendrez un joli commentaire et un ticket inchangé.

    Le temps d'une unité de travail peut aussi être ajusté :

    [WORKUNIT]
TIME_USED: 0.05
[WORKUNIT]

    Sans indication, 0,25 heure est utilisée. Encore une fois : la syntaxe commande.

    Masquer les adresses¶

    Quand quelqu'un répond « à tous », le corps du courriel peut contenir les adresses d'autres personnes. Dans Setup → Setup → Issue setup → Email sending options → Masking email addresses, elles peuvent être remplacées par le caractère générique xxxx@xxxx.xxxx. C'est utile pour éviter de divulguer des contacts dans l'historique du ticket, mais cela ne remplace pas une politique de données décente.

    Microsoft 365 et OAuth¶

    Pour Microsoft 365, enregistrez une application dans Azure AD :

    1. Aller au portail Azure et chercher Azure Active Directory.
    2. App registrations → New registration.
    3. Choisir un nom, un type de compte et une Redirect URI de type Web, par exemple http://localhost/pandora.
    4. Copier Application (client) ID et Directory (tenant) ID.
    5. Créer un Client Secret dans Certificates & secrets et le copier immédiatement : il n'est affiché qu'une fois.
    6. Ajouter les URLs de redirection valides dans Authentication → Add a platform → Web.
    7. Si un utilisateur non administrateur est utilisé, vérifier les permissions d'API et le consentement utilisateur dans Azure AD.

    Ensuite, saisissez Client ID, Tenant ID et Secret dans la configuration SMTP et/ou POP/IMAP de Pandora ITSM. Si les permissions changent, générez un nouveau secret. Les secrets expirent ; les courriels qui en dépendent aussi.

    La procédure détaillée, y compris le consentement avec un utilisateur non administrateur, se trouve dans A4 Intégration avec Microsoft 365.

    Problèmes fréquents¶

    Symptôme Cause probable
    Les courriels ne créent pas de tickets L'adresse de destination ne correspond à aucune file
    Le courriel arrive mais est ignoré L'expéditeur ne correspond pas à Email origin
    Le ticket est créé sans propriétaire Le groupe n'a pas d'utilisateur par défaut
    L'utilisateur n'existe pas Autocréation désactivée ou utilisateur en liste noire
    Les changements par courriel ne s'appliquent pas Syntaxe [INCIDENT] incorrecte
    Les réponses sont mal coupées Message delimiter mal configuré
    Microsoft 365 cesse de fonctionner Secret OAuth expiré
    Les grosses pièces jointes échouent Limite de taille du courriel ou du serveur
