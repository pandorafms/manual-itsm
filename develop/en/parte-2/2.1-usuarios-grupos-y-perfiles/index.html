    Users, groups and profiles¶

    Pandora ITSM is organised around a simple idea that then gets complicated just enough: each user has a profile in a group. The group decides what information they see; the profile decides what they can do with it. A misconfigured permission does not throw an error: it grants access. And that is worse.

    The point of this chapter is the usual one: least privilege is not an audit fashion, it is how you stop a user from breaking what they do not understand. With well-separated groups and tight profiles, the rest of the product works better.

    The model: group, profile and user¶

    The permission structure rests on three concepts:

    • User ID: unique name to log in to the web console.
    • Group: set of users with visibility among themselves. It can be a department, a customer or a company.
    • Profile: set of access bits that defines what the user can do.

    A user can have several profile + group combinations. For example, project manager in one group and ticket operator in another. Permissions are not global: they apply to the group where they are granted.

    On top of this there are Teams: groups of users from different groups who work together on Support, Changes or CRM without duplicating accounts or changing their profiles.

    User management¶

    The manager is in People → User management.

    • To edit, click the User ID.
    • To delete, select the row and click Delete selected, or use Delete user in the Actions column.
    • To create, click Create user +.

    Each user has two switches that should not be confused:

    • Activation: whether the account is enabled.
    • Login enabled: whether they can log in interactively to the console.

    Some users only exist to manage tickets by email: they do not need interactive login.

    On the user form you can choose the Dashboard (welcome screen) they see on login and assign a Company. The company matters: in several sections access depends not only on the group but also on the user's company.

    Users editing their own data¶

    Any user can change their data from People → Edit my user or from the shortcut in the header. There they can see their API 1.0 key in a QR code or generate a token for API 2.0. A user with no profile can also access this menu option.

    User types¶

    Type What it can do
    Grouped user Accesses, views and modifies the information of the groups assigned to them, according to their profile.
    Grouped only by company Like a grouped user, but only sees tickets from users in the same company and group.
    Standalone user In Tickets they only see tickets they created or that are assigned to them. Used to support external customers.
    Super administrator Full access and privileges over every section and group. Always has login enabled.

    A super administrator can be deactivated as an account, but their login remains active. It is a deliberate exception, not an oversight.

    User administrators and licence¶

    Only users with the UM permission or super administrators can create and delete users.

    Pandora ITSM keeps a special count of administrators because the licence limits how many there can be. If the number is exceeded, the console blocks login for the extra administrators; the oldest keep access and the newest are left out. They appear in the list with login disabled.

    To free seats: disable or delete administrators, change their profile to a standard one or expand the licence. Details are in 1.4.

    Profiles and permissions¶

    Profiles are managed in People → Profile management. Each profile has a name, a two- or three-letter abbreviation and a set of access bits.

    At the end of the user form you assign the group and profile combination:

    Each section uses the bits in its own way: tickets combine group and profile; downloads use categories; CRM uses companies and their parent/child hierarchy. There is no single meaning for "having permission": you have to look at the section.

    Projects¶

    Bit What it allows
    PR · View project See the projects the user is assigned to.
    PM · Edit project Create and modify project groups. Counts as an administrator for licensing.

    The project manager can operate on their projects and tasks, and delete them. The owner has the same permissions as the manager. The administrator can do it on any project. Subtasks inherit the parent task permissions.

    Tickets¶

    Bit What it allows
    IR · View tickets See tickets where the user is creator, editor or author of a work unit.
    IW · Edit tickets Create tickets and edit existing ones. Editing is limited to the ticket owner.
    IM · Delete tickets Delete tickets, manage incident types and manage SLAs. Counts as an administrator.
    IC · Close tickets Close tickets without being the owner.

    Escalation and quality¶

    Bit What it allows
    SI · Escalate tickets Assign tickets to a group the user cannot access.
    QA · Quality control See quality reports and closed-ticket reviews.

    Knowledge base¶

    Bit What it allows
    KR · View See knowledge base articles.
    KW · Edit Create and edit articles.
    KM · Manage Delete articles. Counts as an administrator.

    Downloads and directories¶

    Bit What it allows
    FRR · View folders See uploaded directories and files.
    FRW · Edit folders Upload files, update existing ones and create directories.
    FRM · Manage folders Delete files. Counts as an administrator.

    Inventory¶

    Bit What it allows
    VR · View inventory See own objects, public ones, those of the user's company or those specifically assigned.
    VW · Edit inventory Create and edit objects the user can access.
    VM · Manage inventory Delete objects and manage object types. Counts as an administrator.

    Reports¶

    Bit What it allows
    RR · View reports See reports and their data.
    RM · Manage reports Create, modify and delete reports, templates and schedules.

    Wiki¶

    Bit What it allows
    WR · View See the Wiki.
    WW · Edit Create and edit pages.
    WM · Manage Modify, delete and assign users to the Wiki. Counts as an administrator.

    Per-page read and write permissions are configured in the Wiki itself.

    CRM¶

    CRM does not work by groups but by companies and their parent/child hierarchy. If a user has access to a company, they inherit access to its child companies, except the standalone user, who only sees their own.

    Bit What it allows
    CR · View CRM See companies, contacts and deals the user can access.
    CW · Edit CRM Create and edit accessible companies, contacts and deals.
    CM · Manage CRM Modify or delete companies and their structure. Counts as an administrator.
    CA · CRM Admin Advanced CRM administration: forms, marketing and module settings.
    CIR · View invoices See invoices from accessible companies.
    CIW · Edit invoices Create and modify invoices.
    CIM · Manage invoices Delete invoices.
    DRR · Deal Registrations View and manage deal registrations.
    AR · Read calendar See the user's calendar and others according to visibility.
    AW · Edit calendar Add and edit calendar items.
    AM · Manage calendar Delete items, including visible third-party ones. Counts as an administrator.

    Pandora ITSM administration¶

    Bit What it allows
    UM · Manage users Create, edit and manage user profiles. Counts as an administrator.
    DM · Database management Access the database console and run SQL. Counts as an administrator.
    FM · Framework management Access configuration and administrative options. Counts as an administrator.

    Human Resources and ChatBot¶

    Bit What it allows
    HR · Human Resources Edit or delete work units for special tasks: holidays, sick leave, etc.
    CUW · View ChatBot users See the list of users included in the ChatBot.
    COW · View ChatBot operators See the list of operators.
    COM · Manage ChatBot Manage ChatBot users and operators.

    Change management¶

    Bit What it allows
    CHR · Read changes See changes from the teams the user belongs to.
    CHW · Edit changes Create change requests and see the Changes configuration. Can add themselves to or leave the team; only a superadmin or a change manager can add them back.
    CHM · Manage changes See all open and closed changes and edit according to their role. Counts as an administrator.

    Importing users¶

    People → Import users from CSV allows mass user creation. Only administrators have access.

    Group, profile, global profile and avatar are chosen in the console form; the CSV values for those fields are discarded. If the password policy is enabled, it can be applied to imported users.

    CSV columns, in order:

    1. id_user
    2. password
    3. real_name
    4. email
    5. telephone
    6. description
    7. avatar
    8. disabled
    9. id_company
    10. num_employee
    11. enable_login
    12. Custom fields, in the order they exist in the system. If you do not want to give a value, leave a blank space.

    Custom user fields¶

    People → User fields allows you to create your own fields: text, textarea, selector, linked field or checkbox. Only an administrator can define them.

    • Show in list: the field appears as a column in the user list.
    • Show in search: the field appears in the user filter. Search is case-sensitive.

    Group management¶

    People → Groups Management is only visible to users with user-management permissions. They can manage their group or groups and always see the All group, which cannot be edited or deleted.

    Tickets always belong to a group. A default user can be set for new tickets in the group; afterwards the user can escalate tickets within their group if they have permission.

    Group fields:

    Field What it does
    Forced email Enables or disables sending tickets to the group emails.
    Parent Parent group.
    Default user User assigned by default to new tickets.
    Icon Group image.
    Send customer satisfaction email Sends a satisfaction survey on close.
    Open ticket limit Maximum simultaneous open tickets for the group in the last year; for external users, per user.
    Enforced open tickets limit Prevents ticket creation at the limit; otherwise it only warns.
    Total ticket limit Maximum tickets for the group in the last year, open or closed. It is restrictive.
    Ticket SLA SLA applied to the group's tickets.
    Default inventory object Inventory object associated by default with new tickets.
    Email from Address shown as the notification origin.
    Group email Addresses that receive notices about ticket changes in the group.

    Removing a user from a group also removes the profile associated with that group. If the user only had that profile, they are left without enough rights.

    Per-group email queues¶

    People → Group management → Email → Email origin configures the email queues that create tickets. It requires a mail account configured in the console.

    Pandora ITSM can only download from one POP3 or IMAP account, so aliases are used on the mail server to separate destinations. Depending on the destination address, the ticket goes to one group or another, and the sender can be created automatically.

    Teams¶

    People → Teams lets you create work teams that group users from different groups for Support, Changes or CRM, without duplicating accounts or changing their profiles.

    Creating a Team requires two fields:

    1. Name: team name; spaces are allowed. Do not use only spaces: it cannot be edited and will have to be deleted.
    2. Manage: user who will administer the team.

    Optionally, add a mailbox, preferably the manager's, and a description.

    By default the three options are checked: Support, Change and CRM. Each creates its own team in the corresponding feature. At least one is recommended.

    Deleting a Team from this screen also deletes the associated teams in the features. It is irreversible.

    With Add users + you filter enabled users by group or company and add them to the Team. The All option adds all filtered users, or all enabled users if there is no filter.

    A user disabled in user management cannot work on the Team's tasks even if they remain in the list. For Support they need one of the IR, IW, IM, IC, SI bits; for Changes, CHR, CHW, CHM; for CRM, the CR, CW, CM, CA or DRR bits and the right level in companies, invoices and calendar.

    Best practices¶

    • Create one group per department, customer or company; do not mix everything in All.
    • Grant the minimum profile that lets the user work; expanding later is easy.
    • Check Manager Count before creating an administrator (1.4).
    • Disable the accounts of people who leave; a disabled account frees a seat.
    • Do not share admin or give UM to someone who only needs to read.
    • Review profiles after an organisational change.
    • Use Teams for cross-area work, not to duplicate users.
    • Document which profile each group has; the next administrator will thank you.
