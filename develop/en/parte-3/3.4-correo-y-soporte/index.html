    Email and support¶

    Email is the easiest front door for users and the easiest one for administrators to break. In Pandora ITSM it is not enough to configure an SMTP server: you have to decide which mailboxes are read, which senders are accepted, and what happens when a message does not fit any queue.

    The golden rule is simple: if an email does not match a group queue, it is not processed. There is no rescue inbox or apology message. It stays wherever it is, waiting for someone to read it by hand.

    The resulting ticket follows the rules of 3.1 Tickets and incidents and 3.2 Workflow and statuses.

    Two addresses that are not the same¶

    Each group's email configuration has two fields that are often confused:

    • Email destination: addresses or aliases of the mailbox Pandora ITSM reads to create or update tickets. It accepts several addresses and regular expressions, one per line.
    • Email origin: filter of valid senders. Only emails that match this field are accepted for creating or updating tickets. It also accepts several addresses and regular expressions.

    The first says "which mailbox we are talking about"; the second says "who is allowed to write to it". If Email origin is empty, any sender is accepted. Mix them up and you will end up with tickets created by anyone or legitimate emails ignored.

    Email configuration¶

    The general configuration is in Setup → Setup → Email. There are two halves:

    Sending (SMTP)¶

    • System mail from address: sender of notifications.
    • Encryption: none, SSL/TLS, SSLv2, SSLv3, STARTTLS or Microsoft OAuth 2.0.
    • SMTP Host, SMTP Port, SMTP User and SMTP Password.
    • User ID, Client ID, Tenant ID and Secret for OAuth.
    • SMTP Queue retries, Max pending mail and Max. emails sent per execution to control the queue.

    The Test button checks the connection. A "successful test" only proves the server answers; it does not prove the email reaches the destination inbox.

    Receiving (POP/IMAP)¶

    • Encryption, POP/IMAP Host, POP/IMAP Port, POP/IMAP User and POP/IMAP Password.
    • User ID, Client ID, Tenant ID and Secret for OAuth.
    • Select IMAP or POP: IMAP is usually the sensible choice; POP tends to move or delete messages and complicates traceability.
    • Message delimiter: marks where to cut the reply thread.
    • Compatibility: Gmail, Microsoft 365, Outlook, Dreamhost or others.

    If the server requires OAuth, you must connect the application and renew the secret when it expires. An expired secret does not send a polite email: it simply stops receiving.

    Group email queue¶

    The group configuration defines what happens to messages arriving in its queue:

    • Email destination and Email origin.
    • Autocreate users: creates the user if the sender does not exist.
    • Grant access to users: gives them access to the application.
    • Send welcome email and Welcome email: welcome message, with the _password_ macro if the password is sent.
    • Default status, User type, Default company, Default user's profile and Default ticket type.

    Combining Autocreate users and Grant access to users is convenient and dangerous at the same time: anyone who writes to the mailbox can become a user. Enable it only if the origin filter and the network perimeter justify it.

    What happens when an email arrives¶

    1. Pandora ITSM reads the configured mailbox.
    2. It looks for a group queue whose Email destination matches the destination address.
    3. It checks that the sender matches Email origin.
    4. If there is no match, the email is not processed.
    5. If there is a match, it looks for an existing ticket by subject or headers.
    6. If none exists, it creates a new ticket.
    7. If one exists, it adds a work unit, updates the ticket and records the email body as a comment.

    On creation, the ticket takes these values:

    • Creator: user associated with the from address, if it exists or if autocreation is enabled.
    • Editor: the same from user.
    • Group: the queue's group.
    • Owner: the group's default user, if defined.
    • Title: the subject.
    • Description: the body.
    • Notifications: TO and CC addresses other than the queue address.
    • Attachments: the message files.

    Updating a ticket by email¶

    Some fields can be changed with a text block in the message body:

    [INCIDENT]
GROUP: Support
ASSIGNED_TO: operator
PRIORITY: 3
STATUS: Assigned
RESOLUTION: Invalid
[INCIDENT]

    Supported fields:

    Field Value
    GROUP Group name.
    ASSIGNED_TO Owner's login name.
    PRIORITY Number from 0 (lowest) to 5 (highest).
    STATUS Status name.
    RESOLUTION Resolution name.

    If the syntax is not exact, the changes are not applied and the text ends up as a comment. Pandora ITSM does not guess intentions; if you meant to change the status and wrote STATUS : Assigned, you will get a lovely comment and an unchanged ticket.

    The time of a work unit can also be adjusted:

    [WORKUNIT]
TIME_USED: 0.05
[WORKUNIT]

    If not specified, 0.25 hours are used. Again: syntax rules.

    Masking addresses¶

    When someone replies "to all", the email body may carry other people's addresses. In Setup → Setup → Issue setup → Email sending options → Masking email addresses they can be replaced with the wildcard xxxx@xxxx.xxxx. It is useful to avoid leaking contacts into the ticket history, although it is no substitute for a decent data policy.

    Microsoft 365 and OAuth¶

    For Microsoft 365, register an application in Azure AD:

    1. Go to the Azure portal and search for Azure Active Directory.
    2. App registrations → New registration.
    3. Choose a name, account type and a Web Redirect URI, for example http://localhost/pandora.
    4. Copy Application (client) ID and Directory (tenant) ID.
    5. Create a Client Secret in Certificates & secrets and copy it immediately: it is shown only once.
    6. Add the valid redirect URLs in Authentication → Add a platform → Web.
    7. If a non-administrator user is used, review API permissions and user consent in Azure AD.

    Then enter Client ID, Tenant ID and Secret in the SMTP and/or POP/IMAP configuration of Pandora ITSM. If permissions change, generate a new secret. Secrets expire; so do the emails that depend on them.

    The detailed procedure, including non-administrator user consent, is in A4 Microsoft 365 integration.

    Common problems¶

    Symptom Likely cause
    Emails do not create tickets Destination address does not match any queue
    The email arrives but is ignored Sender does not match Email origin
    The ticket is created without an owner The group has no default user
    The user does not exist Autocreation disabled or user in the blacklist
    Email changes are not applied Wrong [INCIDENT] syntax
    Replies are cut incorrectly Message delimiter misconfigured
    Microsoft 365 stops working Expired OAuth secret
    Large attachments fail Email or mail server size limit
