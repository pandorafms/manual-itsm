    Actualización¶

    Actualizar Pandora ITSM no es pulsar un botón y cruzar los dedos. Es una operación de riesgo controlado: hay datos, hay usuarios y hay una versión que funciona. La diferencia entre una actualización aburrida y una tarde de incidentes está casi siempre en lo que se hace antes, no en lo que se pulsa después.

    La tesis de este capítulo es sencilla: si no tienes copia de seguridad, no tienes una actualización; tienes una apuesta. Con copia, ventana y una versión de destino clara, Warp update hace casi todo. Sin eso, el botón más bonito del mundo no te va a salvar.

    Antes de actualizar¶

    Antes de tocar nada, prepara el terreno:

    • Copia de seguridad completa: base de datos, /var/www/html/pandoraitsm y los adjuntos. No basta con el volcado de la base; los ficheros también cuentan.
    • Ventana de mantenimiento: avisa a los usuarios y reserva tiempo para comprobar la consola después.
    • Versión actual y versión destino: anota la versión, el MR y el paquete que tienes. Los verás en About ITSM.
    • Acceso al repositorio de actualizaciones: la actualización en línea necesita registro; la offline funciona con un código temporal.
    • Espacio en disco y memoria: deja margen para descargar, descomprimir y aplicar.
    • Compatibilidad: revisa que PHP y MySQL/Percona de la versión destino sigan dentro de la ventana soportada.
    • Vía de actualización: Warp update en línea, Warp update fuera de línea o tarball heredado.
    • Plan B: si algo falla, ¿vuelves a la copia? ¿Cuánto tardas? ¿A quién avisas?

    No actualices saltando versiones sin confirmar antes la ruta. Un salto mal dado no se arregla con otro salto; se arregla restaurando la copia.

    Si el problema es que la licencia no permite actualizar, este no es el capítulo que lo resuelve: revisa el apartado de licenciamiento (1.4).

    Cómo se actualiza¶

    Hay dos interfaces y tres caminos reales:

    Vía Cuándo usarla Necesita Internet
    Warp update en línea Instalación con salida a Internet y registro Sí
    Warp update fuera de línea Servidores aislados o con acceso restringido No
    Tarball heredado Solo si soporte confirma que sigue vigente No

    Warp update es la vía recomendada. El tarball se mantiene como herencia para casos muy concretos, pero no es el camino que yo elegiría para una 5.0.110 sin consultarlo antes.

    Actualización web en línea¶

    Abre Warp update → Update online.

    La primera vez hay que registrar la instalación con una dirección de correo. El servidor devuelve un UID permanente (pandora_uid) que se guarda para las siguientes actualizaciones. Sin registro, la actualización en línea no arranca: el código lo dice claramente con un «Update online requires registration».

    Con el registro hecho, la pantalla ofrece dos botones:

    • Update to next version: aplica la siguiente versión disponible.
    • Update to latest version: salta a la última publicada.

    Si ya estás en la última versión, ninguno de los dos estará habilitado. No es un fallo: es que no hay nada que instalar.

    Antes de aplicar, revisa el resumen de cambios y correcciones. La descarga puede tardar; no cierres la pestaña ni te vayas a comer mientras el proceso escribe ficheros. Al terminar, revisa el estado del sistema y comprueba la versión en About ITSM.

    Actualización web fuera de línea¶

    Abre Warp update → Update offline.

    Esta vía es para entornos sin Internet o que, por seguridad, no deben hablar directamente con el repositorio. La aplicación de parches offline puede dejar la consola inservible; la copia de seguridad completa no es una sugerencia, es el requisito.

    Si no has registrado la instalación, solicita un código temporal para acceder al repositorio. El flujo es:

    1. Introduce el correo y pulsa Register.
    2. Copia el código y abre el enlace que aparece.
    3. Descarga los ficheros .itsm de la versión que vayas a aplicar.
    4. Vuelve a Update offline y sube cada fichero con BROWSE IT.
    5. Espera al análisis y aplica la actualización con el botón verde.

    En esta pantalla solo se suben ficheros .itsm; los paquetes de servidor no entran por aquí.

    Los ficheros tienen que caber en los límites de PHP:

    post_max_size
upload_max_filesize
memory_limit

    El actualizador avisa si memory_limit baja de 800M. En EL suele estar en /etc/php.ini; en Ubuntu, en /etc/php/8.2/fpm/php.ini o /etc/php/8.4/fpm/php.ini, según la versión instalada. Si el fichero no sube, el problema casi nunca es el fichero: es el límite.

    Actualización con tarball (heredada)¶

    El tarball se descarga en /tmp, se extrae y se ejecuta el script de actualización como root:

    cd /tmp
tar xzf <name_packet>.tar.gz
cd integria_enterprise
./integria_update -p /var/www/html/pandoraitsm

    El script copia el código, ajusta permisos, elimina install.php y protege config.php. Es una herramienta antigua: declara la versión 3.0 y solo contempla una migración de base de datos de 3.0 a 3.1. Para 5.0.110 no lo uses por tu cuenta; confirma antes con soporte que sigue siendo el procedimiento correcto.

    Si aun así lo usas, haz la copia de seguridad primero y comprueba después la versión, el MR, los servicios y los logs. Un tarball mal aplicado se nota tarde.

    Cuando termine, aplica los MR pendientes de la base de datos:

    cd /var/www/html/pandoraitsm
php godmode/um_client/updateMR.php

    El script muestra el MR actual y aplica los pendientes. Si no lo ejecutas, el código puede quedar actualizado y la base de datos quedarse atrás.

    Configuración de Warp Update¶

    En la pantalla de Warp update puedes ajustar la conexión con el repositorio:

    Opción Para qué sirve
    Warp Update URL Dirección del servidor de actualizaciones
    Use secured Warp Update Fuerza TLS en la conexión
    Proxy server / port / user / password Salida a través de un proxy
    Allow no-consecutive patches Permite instalar actualizaciones no consecutivas
    Limit to LTS updates Limita las actualizaciones a versiones LTS

    Contacta con soporte antes de cambiar la URL, el TLS o el proxy. Estas opciones no son un adorno: si las tocas mal, la consola deja de ver el repositorio y parece que el producto se ha roto.

    Sobre Allow no-consecutive patches: en la captura de referencia aparece desactivada, que es la opción recomendada. No la actives sin confirmar el comportamiento de tu versión. Limit to LTS updates viene activo por defecto; si necesitas una versión corriente, tendrás que desactivarlo de forma consciente.

    Warp journal¶

    Warp update → Warp journal muestra el historial de actualizaciones aplicadas. Cada fila guarda:

    • Versión.
    • Tipo.
    • Origen: online u offline.
    • Usuario.
    • Fecha.

    Los datos viven en la tabla tupdate_journal y se pueden filtrar por palabra clave. En una auditoría, este journal vale más que cualquier correo recordando «creo que actualicé en marzo».

    Después de actualizar¶

    Al terminar, vuelve a iniciar sesión. Después comprueba, en este orden:

    1. About ITSM: versión, MR y paquete. Deben haber cambiado.
    2. Servicios: Apache, PHP-FPM y MySQL/Percona activos.
    3. Cron: integria_cron.php, crm_cron.php y campaign_cron.php siguen en /etc/crontab.
    4. Logs: pandora_itsm.log y /var/log/php-fpm/www-error.log.
    5. Prueba funcional: login, abrir un ticket, consultar inventario, entrar en CRM y lanzar una campaña de prueba.
    6. Warp journal: la actualización aparece con la versión correcta.

    Si algo falla, no improvises sobre la instalación a medio actualizar. Restaura la copia, vuelve a la versión anterior y abre una incidencia con los logs. Un sistema restaurado a tiempo es mejor que uno «casi actualizado» durante una semana.

    Problemas frecuentes¶

    Síntoma Causa probable Comprobación
    No aparece ninguna actualización Sin registro, sin conexión o LTS activo Revisa pandora_uid, la red y Limit to LTS updates
    Error de memoria al aplicar memory_limit bajo Súbelo a 800M o más
    El fichero offline no sube Extensión, tamaño o límites de PHP Revisa .itsm, post_max_size y upload_max_filesize
    La consola queda inservible tras un parche Parche incompleto o incompatible Restaura la copia y revisa el log
    El MR no cambia Proceso de MR pendiente Revisa updateMR.php y el journal
    Los servicios no arrancan Dependencias o configuración Revisa Apache, PHP-FPM, MySQL y sus logs
    El cron ha desaparecido Actualización que reescribe /etc/crontab Vuelve a añadir las tres entradas
    La versión no cambia en About ITSM Actualización no aplicada o caché Revisa el journal y vuelve a iniciar sesión

    Siguientes pasos¶

    Con la actualización cerrada:

    • Revisa las versiones y el ciclo de soporte (1.3).
    • Revisa el licenciamiento si la actualización estaba limitada por licencia (1.4).
    • Programa copias de seguridad y monitorización (Parte 12).
    • Anota la versión aplicada y la fecha en el journal.
    • Planifica la siguiente actualización antes de que te pille el calendario.
