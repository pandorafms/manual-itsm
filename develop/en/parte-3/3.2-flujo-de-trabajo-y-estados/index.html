    Workflow and statuses¶

    A ticket status is the closest thing support has to a traffic light. While nobody touches it, the ticket looks alive; when everyone changes it at will, the traffic light becomes decoration. Pandora ITSM offers two mechanisms to make the flow meaningful: status mapping and workflow rules.

    The first says where a ticket may go. The second decides what happens when it gets there. Using one without the other is like painting road signs on a road with no asphalt.

    Statuses are not labels¶

    A ticket has a life cycle and several possible statuses. The main ones are:

    Status What it means
    New The ticket has just been opened. The first-response SLA is measured here.
    Pending Customer The customer has the last word; their answer is expected.
    Pending Support Support has the last word; the response SLA keeps running.
    Re-opened A closed ticket becomes active again. For SLA purposes it behaves like support.
    Pending to be Closed It is solved, but confirmation or formal closure is pending.
    Pending on a third person It depends on a third party. Inactivity and response stop, although resolution time may keep running.
    Closed The ticket is closed. When it reaches this status, the epilogue appears.

    The epilogue is not decoration: it explains what was done and why. A closed ticket without an epilogue is a ticket nobody will be able to reinterpret six months later.

    Status mapping¶

    Status mapping is configured in Support → Workflow → Status mapping. It defines which statuses and resolutions are available at each point and forces the ticket through the phases the organisation considers necessary.

    A simple example: a new ticket can only move to assigned; from there, to pending closure; and from there, to closed with resolution "solved" or "incomplete". If it is closed as incomplete, it can be reopened and sent back into the loop.

    By default, any super administrator can change a ticket status —unless it is blocked— without respecting the mapping. It is a deliberate escape valve: if the flow is designed as a cage, someone will eventually open it with a hammer.

    Workflow rules¶

    Rules are managed in Support → Workflow → Workflow rules and only super administrators can create or edit them. Each rule has a description and an execution mode:

    • Cron: evaluated on each cron run, usually every five minutes.
    • Real time: evaluated when a ticket is created or edited.

    By default, only open tickets are checked. To include closed tickets, enable Check closed tickets when running workflow rules in Setup → Setup → Issue setup → Workflows.

    Pandora ITSM ships with a set of sample rules disabled by default. You can modify and enable them, or create new ones from scratch. Before enabling someone else's rule, read its conditions: an inherited rule may do things that no longer make sense in your organisation.

    Conditions¶

    Each rule can have one or more conditions. When creating them, you choose ticket fields and define how they combine:

    • Match all fields: all must be met.
    • Match any field: one is enough.
    • No match: met when there is no match.

    Details that change the result:

    • Priority is numeric, and a higher priority does not include lower ones. If you filter by 3, you are not filtering by 1 and 2 as well.
    • When you choose a ticket type, its custom fields appear and can be used in the condition.
    • The default relationship between conditions in the same rule is OR: if one is met, the rule runs.
    • Conditions can be reordered; evaluation order matters when there are several actions.

    Actions¶

    When the conditions are met, the rule runs one or more actions:

    • Change priority.
    • Change owner.
    • Change group.
    • Change status.
    • Send an email.
    • Add a work unit.
    • Change the update date.
    • Change the resolution.
    • Run a command on the server or a custom script.
    • Block or unblock.
    • Change the type.

    The most useful actions are usually the boring ones: assign the ticket to the right group, raise the priority when it has been idle too long, and notify the owner. The spectacular actions —running commands, changing types, blocking— should have a very short guest list.

    Macros¶

    Actions accept macros that are replaced with ticket values:

    Macro Value
    _access_url_ Direct URL to the ticket
    _author_ Ticket creator
    _companymanager_ Manager of the ticket's company
    _creation_timestamp_ Creation date and time
    _fullname_ Recipient's full name
    _id_group_ Group identifier
    _id_priority_ Priority identifier
    _id_resolution_ Resolution identifier
    _id_status_ Status identifier
    _incident_auth_email_ Creator's email
    _incident_closed_by_ User who closed the ticket
    _incident_epilog_ Ticket epilogue
    _incident_group_email_ Group email
    _incident_id_ Ticket identifier
    _incident_own_email_ Owner's email
    _incident_title_ Title
    _name_group_ Group name
    _name_priority_ Priority name
    _name_resolution_ Resolution name
    _name_status_ Status name
    _owner_ Owner
    _sitename_ Site name
    _type_tickets_ Ticket type
    _update_timestamp_ Last update
    _username_ Recipient's login name

    Custom fields also work as macros with the format _field_name_. If the name has spaces or strange characters, the macro may become a surprise; consistent naming, please.

    Practical recipes¶

    Three rules that usually pay for the effort:

    1. High priority, immediate notice: if priority is 5 and status is New, change the owner to the on-call team and send an email with _incident_id_, _incident_title_ and _access_url_.
    2. Silent customer: if status is Pending Customer and the last update is older than the configured days, send a reminder and, if appropriate, move to Pending to be Closed.
    3. Orderly closure: when moving to Closed, require resolution and epilogue, and send the satisfaction survey if the group has it enabled.

    Common mistakes¶

    Symptom Likely cause
    The rule never runs Conditions too restrictive or rule disabled
    It runs on closed tickets it should not touch Closed-ticket check token enabled
    It changes status and nothing else happens The action is in another rule with different conditions
    The email arrives without data Wrong macro or empty field
    The flow gets stuck Status mapping too rigid and with no escape valve

    The metrics that measure this flow are explained in 3.3 SLA, escalation and quality.
