    SLA, escalation and quality control¶

    An SLA (service level agreement) is a promise with a clock. If the clock only runs when convenient, the promise becomes literature. Pandora ITSM measures four different times and compares them with the limits the organisation has defined; the rest is interpreting the numbers without fooling yourself.

    Where it is configured¶

    SLAs are managed in Support → View SLA and assigned at group level. The ticket's group determines which SLA applies, although the default SLA can be changed during creation and the group SLA can be reloaded with the reload button.

    The main fields:

    Field What it measures
    First response SLA (in hours) Maximum time until the owner's first response.
    SLA Base Informative relationship with another SLA.
    SLA Type Normal, third party or both.
    Max. response time (in hours) Maximum time between the creator's last work unit and the next response.
    Max. resolution time (in hours) Maximum ticket lifetime until resolution.
    Max. tickets at the same time Maximum number of open tickets at once.
    Max. ticket inactivity (in hours) Maximum time without any update.
    Disable SLA on holidays Excludes holidays from the calculation.

    SLA Type changes the set of tickets included in the calculation:

    • Normal: tickets that are neither closed nor pending on a third party.
    • Third party: only those pending on a third party.
    • Both: all tickets that are not closed. In this case, a specific inactivity limit can be configured for third parties.

    The four clocks¶

    The ticket view and statistics show four metrics. All have the same structure: Used, Limit and Deviation.

    Metric What it measures
    First response (FRT) From opening to the agent's first response.
    Response time Between later responses from the creator and the agent. For it to count correctly, the status must be Pending Support.
    Inactivity time Since the ticket's last update.
    Resolution (TTR) From creation to resolution.

    Deviation is the part most often misunderstood: if what was used is less than the limit, the deviation is the time left over (positive); if it is greater, it is the delay. When the limit is exceeded, the SLA alert fires.

    Time windows and holidays¶

    An SLA does not have to count twenty-four hours a day. Scheduled defines the windows in which it is counted, with a simple or detailed mode. The detailed mode can adjust by minutes, but requires cron to run at that granularity. If cron runs every five minutes, promising minute-level precision is a creative way to lie.

    Disable SLA on holidays excludes holidays. Holidays are defined in Setup → Setup → Issue setup → Customization → Special day, where you can also indicate whether they are working days.

    What "the SLA will breach" means¶

    It means the system will send an email to the ticket owner warning that one of the criteria of the associated SLA has been breached. The SLA applies by group, so a ticket can inherit a different SLA when it changes group.

    The ticket list can be filtered by breached or non-breached SLA, and the ticket view shows a histogram with met and unmet periods, plus a compliance percentage by date range. Those metrics are also available through the API and support reports.

    Escalation¶

    Escalating is not "pass the ticket to someone else and forget about it". A healthy escalation changes at least one of these three things:

    • Owner: from one person to another or to a team.
    • Group: from first level to second level, or to a specialised team.
    • Priority: because the real impact has changed.

    Workflow rules are how you automate those changes: reassign to the on-call team, raise the priority when the ticket has been in Pending Support for too long, or notify the manager when a threshold is crossed. Manual escalation is still needed for what no form anticipated.

    Quality control¶

    Quality assurance (Q/A) and feedback are configured at two levels:

    • General: Setup → Setup → Issue setup → Ticket behavior → Disable ticket score disables rating.
    • Per group: People → Groups management → Send customer satisfaction email decides whether the survey is sent on closure.

    By default, when a ticket is closed the creator is asked how it was resolved. The rating can only be good or bad, with optional text. It is associated with the ticket and its owner, and only users with Q/A permissions and the creator can see it.

    If the rating is negative and Survey Questions is enabled, a survey with the configured options is shown. It can only be answered once. A survey that arrives late, or asks the same thing as the ticket, does not improve quality: it only generates more email.

    Creation limits¶

    In People → Groups management you can limit tickets per group and user:

    • Total ticket limit: maximum total tickets, open or closed.
    • Open ticket limit: maximum open tickets at the same time.

    The limit can be forced (no more tickets allowed) or only warn. A value of 0 means no limit. The calculation counts tickets from the last year from the current date, not the entire history of humanity.
