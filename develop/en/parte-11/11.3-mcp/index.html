    MCP (Model Context Protocol)¶

    Pandora ITSM publishes an MCP server so an AI agent can query tickets, companies, contacts, deals, notes, email, schedules and web tracking without leaving the console. It is not a chatbot: it is a read-only layer that speaks the standard protocol of MCP clients and authenticates with OAuth 2.1.

    The idea is simple: the agent stops copying and pasting data from the console and asks directly. The server answers with the same ACLs, the same audit trail and the same limits as API v2. The difference is the caller, which is now a model rather than a script.

    This chapter covers the Pandora ITSM MCP server: which tools it exposes, how to enable it, how a client authenticates, what each tool returns and where access stops. API v2 remains the way to write and to integrate applications; MCP is a read-only façade for agents.

    What it is and what it allows¶

    MCP (Model Context Protocol) is an open protocol that lets a client (Claude Code, Cursor, OpenCode, Codex, a web connector) discover tools and call them against a server. Pandora ITSM implements the server side over HTTP, with JSON-RPC 2.0 and OAuth 2.1 authentication.

    A read-only server¶

    Every tool in the catalogue declares readOnlyHint: true. The server does not create, update or delete tickets, companies or any other object. It does not attach files or send email either. If the agent needs to write, it must use API v2 with an API token and the corresponding ACLs.

    The catalogue is grouped into seven areas:

    Area Tools Purpose
    Companies company_search, company_get, activity_feed Find accounts, read their profile and see recent activity.
    Tickets ticket_search, ticket_get Find tickets and read their status, description, tracking and work units.
    Contacts contact_search, contact_get Find people at a company and read their profile.
    Deals deal_search, deal_get Query the pipeline, the forecast and the detail of a deal.
    Notes, email and schedules note_list, email_list, schedule_list Read notes, email metadata and tasks, meetings or reminders.
    Web tracking webtracking_summary Count attributed contacts by source, category, campaign or month.
    Reference reference_data Translate identifiers and enums, and discover the allowed filters.

    What you can ask¶

    Some real examples of what an agent can resolve with these tools:

    • "What is the status of ticket 4321 and what happened in the latest replies?"
    • "Summarise Acme's activity over the last week."
    • "Which deals has salesperson jlopez moved this quarter, and what is the weighted forecast?"
    • "How many contacts attributed to Google Ads arrived this month?"
    • "Give me the closed tickets in the Support group between 1 and 15 November."

    The agent chains searches and reads: first it resolves identifiers with reference_data, then it searches with *_search, and finally it opens the detail with *_get.

    What it does not do¶

    • It does not write. There are no create, update or delete tools.
    • It does not return email bodies or recipients; only metadata.
    • It does not return email or phone numbers in company and contact searches. To get them, request the detail of a specific contact.
    • It does not replace API v2 or the console. It is a read-only view for agents.
    • It does not share tokens with API v2: an OAuth token issued for MCP is only valid on /mcp.

    Requirements¶

    Requirement Detail
    HTTPS Cloud MCP clients require HTTPS. OAuth redirects only allow HTTPS or loopback HTTP (localhost, 127.0.0.1, [::1]).
    Public URL Public MCP URL must be an absolute HTTPS URL ending in /mcp. Without it, MCP cannot be enabled and OAuth metadata cannot be published.
    API ACL The List of IP with access to API list (api_acl) also applies to /mcp and the OAuth endpoints. It must include the egress IPs of the clients. With cloud clients, add their ranges or open the list to *; the real control is then the MCP policy and OAuth.
    User and permissions The user who authorises access must be active, included in the MCP policy and hold the product permissions required by each tool.
    Compatible client The client must support remote MCP servers over HTTP and OAuth 2.1 with dynamic registration and PKCE.

    Enabling and configuring MCP¶

    Configuration lives under Setup → Setup → MCP setup. Only administrators can open and save it. The page is organised into tabs: Status, Discovery, Connect, Access policy, Runtime settings and Authorizations.

    The global switch¶

    Enable MCP server turns the server on or off. While it is off, the endpoint returns a policy error and clients cannot use any tool. When it is enabled, the page shows the remaining tabs and the getting-started guide:

    1. Enable MCP.
    2. Choose who can use it and set the public URL.
    3. Check the API ACL.
    4. Connect the client; the first connection opens the consent page.

    MCP cannot be enabled without Public MCP URL. The server needs a trusted URL to build the OAuth issuer and the discovery documents, and it never derives them from the Host header.

    Status and readiness checklist¶

    The Status tab shows the endpoint and five checks:

    Check Meaning
    MCP enabled The global switch is on.
    Access policy At least one user or group is allowed, or the policy allows everyone.
    HTTPS The console is served over HTTPS.
    Public MCP URL The public URL is configured.
    API ACL The API ACL is not restricted to 127.0.0.1 or localhost.

    A red dot does not necessarily block saving, but it explains why a client cannot connect. The API ACL check is the one most often forgotten: if the list only allows loopback, a client arriving from another IP receives 401 before the OAuth dance even starts.

    OAuth discovery¶

    The Discovery tab shows the two URLs a client queries before authenticating:

    https://<host>/.well-known/oauth-protected-resource
https://<host>/.well-known/oauth-authorization-server

    Both documents must be published at the domain root. If Pandora ITSM runs in a subdirectory or behind a proxy, the web server must rewrite or align those paths; in that case the discovery URL appends the resource path. The Discovery tab shows the two exact URLs for the installation and includes a Check button that makes a real request and marks the result.

    Apache configuration¶

    The API v2 serves the documents at /pandoraitsm/api/v2/.well-known/..., but the client looks for them at the domain root. Those paths must be rewritten in the HTTPS virtual host. Add the rules to your 443 virtual host; the block below shows the minimum context. With the installation under /pandoraitsm and the public URL https://itsm.example.com/pandoraitsm/api/v2/mcp:

    <VirtualHost *:443>
    ServerName itsm.example.com
    DocumentRoot /var/www/html

    RewriteEngine On

    # Protected resource (RFC 9728)
    RewriteRule ^/\.well-known/oauth-protected-resource/pandoraitsm/api/v2/mcp$ \
        /pandoraitsm/api/v2/.well-known/oauth-protected-resource [PT,L]

    # Authorization server (RFC 8414)
    RewriteRule ^/\.well-known/oauth-authorization-server/pandoraitsm/api/v2$ \
        /pandoraitsm/api/v2/.well-known/oauth-authorization-server [PT,L]

    # Fallback when the client requests the root path without the resource path
    RewriteRule ^/\.well-known/oauth-protected-resource$ \
        /pandoraitsm/api/v2/.well-known/oauth-protected-resource [PT,L]

    RewriteRule ^/\.well-known/oauth-authorization-server$ \
        /pandoraitsm/api/v2/.well-known/oauth-authorization-server [PT,L]
</VirtualHost>

    Replace pandoraitsm with the real directory of the console. If the installation is at the root, change /pandoraitsm/api/v2 to /api/v2 and remove pandoraitsm from the paths. The first two rules handle the canonical path with the resource path; the last two cover clients that request only /.well-known/.... [PT,L] lets Apache pass the request to the API front controller without changing the URL the client sees.

    Make sure mod_rewrite is enabled and that the rules are in the 443 virtual host, not in a .htaccess file (if you put them in .htaccess, remove the leading slash from the patterns). Then reload Apache:

    # RHEL, AlmaLinux, Rocky Linux
sudo systemctl reload httpd

# Debian, Ubuntu
sudo systemctl reload apache2

    Check both URLs from an IP allowed in api_acl:

    curl -s https://itsm.example.com/.well-known/oauth-protected-resource | python3 -m json.tool
curl -s https://itsm.example.com/.well-known/oauth-authorization-server | python3 -m json.tool

    The first must return resource with the public URL and authorization_servers; the second must return issuer and the endpoints. If you get the console HTML or a 404, the rule is not matching: check the ServerName, the DocumentRoot and that mod_rewrite is loaded. If there is a reverse proxy in front, it must forward /.well-known/oauth-* to this Apache.

    The protected resource document declares the resource, the issuer and the itsm.read scope. The authorisation server document declares the authorisation, token, registration and revocation endpoints, the authorization_code flow, refresh, PKCE S256 and the none client authentication method.

    Access policy¶

    The Access policy tab decides which users can use MCP. There are four lists and two recursion switches:

    • Allowed users and Blocked users.
    • Allowed groups and Blocked groups.
    • Include child groups for allowed groups.
    • Include child groups for blocked groups.

    Evaluation is cumulative and blocking wins:

    1. If MCP is disabled, everything is denied.
    2. If the user is disabled, it is denied.
    3. If the user is in Blocked users, it is denied.
    4. If the user belongs to a blocked group, it is denied.
    5. If the policy allows all users or all groups, or the user is in Allowed users, it is allowed.
    6. If the user belongs to an allowed group, it is allowed.
    7. In any other case, it is denied.

    The interface no longer shows the "allow everyone" switches; the API keeps them for compatibility. If they are enabled through the API, the resulting policy allows everyone and the block lists still take precedence.

    Runtime settings¶

    The Runtime settings tab controls the server behaviour:

    Setting What it does Default Range
    Maximum rows per tool call Caps how many rows a tool can return in one call. Each tool schema already allows up to 50; this setting can reduce it. If the client requests more rows than allowed, it gets the configured value. 50 1–50
    Requests per minute and token Sets how many requests each token can make per minute. When exceeded, the response is 429 with Retry-After. 0 disables the limit. 60 0–1000
    Audit retention (days) Decides how many days calls are kept in the audit log before being purged. 90 1–3650
    Public MCP URL Public endpoint URL. It is used to build the OAuth issuer and the discovery documents; without it, MCP cannot be enabled. It must use HTTPS and end in /mcp. empty HTTPS URL
    Authorization lifetime (days, 0 = unlimited) Sets the maximum lifetime of an authorisation from the moment the user approves consent. When it expires, the client must authorise again. 0 makes it unlimited. 90 0–3650
    Allowed redirect hosts Decides which hosts a client may redirect to after consent. One host per line; *.example.com includes subdomains; empty allows any host. claude.ai, chatgpt.com, localhost, 127.0.0.1 Up to 50

    Public MCP URL does not accept credentials, a query string or a fragment. If the installation is behind a proxy, the URL must be the one the client sees, not the server's internal URL.

    Authorisations¶

    The Authorizations tab lists the applications each user has authorised: client name, redirect hosts, user, last IP, authorisation date, last use, expiry and a revoke button. Revoking an authorisation deletes that user's tokens for that client; it does not affect other users of the same client.

    Each user can view and revoke their own authorisations from the MCP applications tab of their user profile.

    Configuring through the API¶

    The policy can also be read and written with API v2, using an administrator token. These endpoints do not accept MCP OAuth tokens.

    GET /api/v2/mcp/permission
PUT /api/v2/mcp/permission

    The PUT accepts the policy fields and leaves omitted fields unchanged:

    {
  "enabled": true,
  "allowedUsers": ["admin", "support"],
  "blockedUsers": ["temporary"],
  "allowedGroups": [1, 26],
  "blockedGroups": [],
  "allUsersAllowed": false,
  "allGroupsAllowed": false,
  "allowedGroupsRecursion": true,
  "blockedGroupsRecursion": false
}

    The response returns the saved policy. A 400 means an invalid value; a 403 means the token does not belong to an administrator.

    Connecting an MCP client¶

    The Connect tab offers the URL, a prompt ready to paste into the agent and the alternative for web chats. The prompt is in English because the agent consumes it, not the user.

    The agent prompt¶

    Connect yourself to the Pandora ITSM MCP server.

Server
- Name: itsm
- Transport: Streamable HTTP (remote MCP server)
- URL: https://itsm.example.com/pandoraitsm/api/v2/mcp
- Authentication: OAuth 2.1 with dynamic client registration and PKCE. The server publishes
  its metadata under /.well-known/oauth-protected-resource. Do not ask me for an API key or
  a client secret.

Steps
1. Identify which MCP client you are (Claude Code, Cursor, OpenCode, Codex, VS Code...) and add
   the server with that client's official method: its CLI command if it has one, otherwise its
   MCP configuration file. Use the user-level scope unless I say otherwise.
2. Keep the existing configuration: add or update only the "itsm" entry, and show me the change
   before writing any file.
3. Start the authorization (for example, /mcp in Claude Code). A Pandora ITSM page opens in the
   browser: I will sign in and approve the access myself. Never ask for my password.
4. Once connected, list the available tools and show them to me. They are read-only.

If the URL is not reachable or its certificate is not trusted, stop and tell me the exact error.
Do not disable TLS verification. If you cannot configure MCP servers yourself (for example, a web
chat), tell me to add a custom connector with the URL above instead.

    OpenCode¶

    OpenCode adds the server with its CLI and stores the configuration at user scope:

    opencode mcp add itsm --url https://itsm.example.com/pandoraitsm/api/v2/mcp --global
opencode mcp list

    Then, in the interface, open /mcps, select itsm and complete authorisation in the browser.

    Claude Code¶

    claude mcp add --transport http itsm https://itsm.example.com/pandoraitsm/api/v2/mcp --scope user
claude mcp list

    Inside Claude Code, /mcp shows the server and starts sign-in. The token is stored and refreshed automatically.

    Cursor and other clients with a configuration file¶

    Many clients read an mcpServers entry with the server URL:

    {
  "mcpServers": {
    "itsm": {
      "type": "http",
      "url": "https://itsm.example.com/pandoraitsm/api/v2/mcp"
    }
  }
}

    The exact name of the transport field changes between clients (type, transport, streamable-http). If the client does not support remote HTTP servers or cannot do OAuth with dynamic registration, it will not connect: use the agent prompt or a compatible client.

    Claude.ai and ChatGPT¶

    Web chats cannot configure themselves. In Settings → Connectors → Add custom connector, paste the public server URL and complete consent. The application then appears in the authorisation list.

    Checking the connection¶

    A successful connection returns the catalogue of 14 tools with tools/list. If the client shows zero tools, check in this order: URL, certificate, API ACL, Public MCP URL, MCP policy and user permissions.

    How to call a tool¶

    {
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "ticket_search",
    "arguments": {
      "freeSearch": "printer",
      "status": "ASSIGNED",
      "size": 10
    }
  }
}

    Arguments must be an object. An unknown tool name returns -32601; an argument that is not in the schema returns -32602/isError.

    Common parameters¶

    Only list tools share these parameters. *_get does not paginate or sort.

    Pagination¶

    Parameter Type Default What it does
    page integer ≥ 0 0 Page, starting at zero.
    size integer 1–50 20 Rows per page. webtracking_summary defaults to 50.

    The response includes:

    {
  "pagination": {
    "total": 3252,
    "page": 0,
    "size": 20,
    "totalPages": 163,
    "nextPage": 1
  }
}

    nextPage is null on the last page. Maximum rows per tool call reduces size below the maximum of 50 allowed by the schema.

    Sorting¶

    Parameter Type What it does
    sortField string Sort field. Each tool publishes its list.
    sortDirection ascending or descending Sort direction.
    sortMultipleFields object Up to three fields with their direction. Cannot be combined with sortField/sortDirection.

    Example:

    {
  "sortMultipleFields": {
    "priority": "descending",
    "startDate": "ascending"
  }
}

    Generic filters¶

    Company, contact, deal, schedule, note, email and activity tools accept fieldConditions: up to 10 conditions on real columns. jsonPath and derived aliases are not supported.

    {
  "fieldConditions": [
    { "field": "createdAt", "operator": ">=", "value": "2026-01-01" },
    { "field": "country", "operator": "in", "value": ["ES", "FR"] }
  ]
}

    Supported operators:

    Operator Use
    =, !=, <>, >, <, >=, <= Simple comparison.
    like, not_like Text match.
    in, not_in List of up to 50 values.
    between, not_between Two-value range.
    is_null, is_not_null Null or not null.
    is_empty, is_not_empty Empty or not empty.

    ticket_search does not accept fieldConditions; use its named filters (status, priority, idGroup, idUser, dates). To find out which fields and operators each tool accepts, call reference_data with types: ["filter_fields"].

    Dates¶

    Dates are sent as YYYY-MM-DD. The server also accepts an ISO 8601 date and time and keeps the date. In ranges, the upper bound includes the whole day when the tool declares it so (createdTo, lastActivityTo). An invalid date returns isError with the field name.

    Identifiers and reference data¶

    Identifiers are the console's. They are not invented or derived from the name. Before filtering by status, priority, group, pipeline or stage, request the tables from reference_data:

    {
  "jsonrpc": "2.0",
  "id": 4,
  "method": "tools/call",
  "params": {
    "name": "reference_data",
    "arguments": {
      "types": ["ticket_statuses", "ticket_priorities", "groups"]
    }
  }
}

    Companies¶

    company_search¶

    Finds companies by text, tags, dates, billing or generic conditions. It does not return email or phone.

    Parameter Type Notes
    freeSearch string Name or comments.
    tags integer[] All tags must match.
    dateBegin, dateEnd date Last update, inclusive.
    createdFrom, createdTo date Creation date, inclusive.
    lastActivityFrom, lastActivityTo date Last activity, inclusive.
    minBilling, maxBilling integer Billing range.
    fieldConditions object[] Up to 10 conditions.
    sortField string idCompany, name, createdAt, lastUpdate, lastActivityAt, country, manager, billing.

    Returns idCompany, name, idCompanyRole, country, manager, createdAt, lastActivityAt, activeContractDates and billing.

    company_get¶

    Parameter Type Notes
    idCompany integer ≥ 1 Required.
    detail boolean false by default. With true, adds address, idTax, comments, parent company, payment conditions, dates, billing and custom fields.

    activity_feed¶

    Parameter Type Notes
    idCompany, idUser integer / string Filter by company or salesperson.
    fromDate, toDate date Activity range.
    freeSearch string Free text.
    fieldConditions object[] Up to 10 conditions.
    sortField string idCompanyActivity, createdAt, idCompany, idContact, idDeal, section, action.

    Returns references to company, contact, deal, note, email, schedule, meeting, form, contract and invoice, without message bodies.

    Tickets¶

    ticket_search¶

    Parameter Type Notes
    freeSearch string Title or description.
    idCompany integer Current company of the creator, not a historical snapshot.
    status string NEW, UNCONFIRMED, ASSIGNED, REOPENED, VERIFIED, PENDING_THIRD_PERSON, CLOSED, NOTCLOSED.
    priority string INFORMATIVE, LOW, MEDIUM, SERIOUS, VERY_SERIOUS, MAINTENANCE.
    idGroup integer ≥ 0 Group.
    idUser string Ticket owner.
    fromDate, toDate date Creation date, inclusive.
    sortField string idIncidence, startDate, updateDate, closeDate, title, status, priority, idGroup, owner, idCreator.

    Returns idIncidence, idCompany, startDate, closeDate, updateDate, title, owner, status, priority, idGroup and resolution. Visibility is enforced by the user's group ACL.

    ticket_get¶

    Parameter Type Notes
    idIncidence integer ≥ 1 Required.
    includeTracks boolean true by default; includes up to size tracking entries.
    includeWorkunits boolean false by default; includes work units.
    size integer 1–20 Tracking or work unit rows.

    Returns the ticket data (idIncidence, idCompany, title, description, status, priority, owner, idGroup, idCreator, startDate, updateDate, closeDate, resolution, epilog, idParent, idIncidenceType). Description and epilog are truncated to 4000 characters; tracking and work units to 2000.

    Contacts¶

    contact_search¶

    Parameter Type Notes
    freeSearch string Name, email or description.
    idCompany integer Company.
    tags integer[] All tags must match.
    companyRoles integer[] Company roles.
    disabled boolean Filter disabled contacts.
    fieldConditions object[] Up to 10 conditions.
    sortField string idContact, fullname, createdAt, updatedAt, idCompany.

    It does not return email or phone. Returns idContact, idCompany, companyName, fullname, position, disabled, manager, createdAt and updatedAt.

    contact_get¶

    Parameter Type Notes
    idContact integer ≥ 1 Required.
    detail boolean false by default. With true, adds email, phone, mobile, description, custom fields and newsletter subscription.

    Deals¶

    deal_search¶

    Parameter Type Notes
    freeSearch string Name or description.
    idCompany, idOwner integer / string Company or salesperson.
    idPipeline, idStage integer Pipeline or stage.
    stages integer[] Several stages.
    createdFrom, createdTo date Creation.
    updatedFrom, updatedTo date Last update.
    fieldConditions object[] Up to 10 conditions.
    sortField string idDeal, name, amount, closeDate, startDate, createdAt, updatedAt, lastActivity, idOwner, idCompany.

    Returns idDeal, name, idOwner, idCompany, idPipeline, idStage, amount, closeDate, startDate, updatedAt and lastActivity. It adds aggregates.liveOperations and aggregates.forecast for the same filter.

    deal_get¶

    Parameter Type Notes
    idDeal integer ≥ 1 Required.
    detail boolean false by default. With true, adds description, custom fields and creation date.

    Notes, email and schedules¶

    note_list¶

    Parameter Type Notes
    idCompany, idContact, idDeal, idContract integer Object the note belongs to.
    idUser string Author.
    freeSearch string Note text.
    fromDate, toDate date Creation.
    fieldConditions object[] Up to 10 conditions.

    Permissions, audit and limits¶

    MCP policy and product ACLs¶

    The MCP policy decides who can enter. Then each tool applies the product ACL:

    Tool Permission checked
    company_search CR
    company_get CM
    activity_feed CR
    ticket_search Group ACL of the ticket list.
    ticket_get IR plus the ticket group ACL.
    deal_search CR
    deal_get CR
    contact_search CM
    contact_get CM
    note_list CR
    email_list CR
    schedule_list CRM
    webtracking_summary CM
    reference_data CR

    A user allowed in MCP but without the product permission receives a tools/call with isError: true and the ACL message. There is no way to bypass the ticket group ACL: both the list and the detail apply it.

    Rate limit¶

    The limit is per token and per minute. The default is 60 requests per minute. All calls count, not only tools/call. When exceeded, the response is 429 with Retry-After and a JSON-RPC -32002 error.

    The counter is stored in tmcp_rate_limit and cleaned up opportunistically. A value of 0 disables the limit; do not do that on an exposed installation.

    Audit¶

    Every tool call is recorded in tmcp_audit with:

    Field Content
    id_user User who authorised the token.
    token_uuid Token UUID.
    tool Tool name.
    arguments Arguments, with secrets redacted and long texts trimmed.
    rows_returned Rows returned.
    duration_ms Duration.
    status ok, error or denied.
    error_code, error_message Failure reason, if any.
    ip Source IP.
    mcp_session Request identifier.
    created_at Date.

    Arguments are redacted if the key contains pass, token, secret, authorization, cookie or session; texts are cut to 500 characters and the structure to three levels and 50 keys. Denied or rate-limited tool calls are also recorded.

    Administrators can see the calls under Setup → Audit log → MCP, a tab that only appears when MCP is enabled. The default retention is 90 days.

    Privacy and truncation¶

    Tool What is trimmed
    company_search, contact_search Do not return email or phone.
    contact_get With detail=true, returns email, phone and mobile.
    email_list Does not return body or recipients.
    ticket_get Description and epilog to 4000 characters; tracking and work units to 2000.
    note_list Text to 1000 characters.
    schedule_list Description to 1000 characters.

    These limits are not configurable per tool. The goal is to keep an agent from dumping half the database into the model context.

    Troubleshooting¶

    Symptom Likely cause Fix
    The client cannot discover OAuth (404 on /.well-known/...). The documents are not published at the domain root or the proxy does not rewrite them. Check the Discovery tab and the web server rewrite.
    401 before the browser opens. The client IP is not in api_acl. Add the IP or range under Setup → Setup → General setup.
    403 when enabling MCP. Public MCP URL is missing or the licence is invalid. Set the HTTPS URL ending in /mcp and check the licence.
    503 on the metadata. Public MCP URL is empty. Set it; the OAuth issuer is never derived from Host.
    Consent is requested again and again. The authorisation expired (Authorization lifetime) or the refresh failed. Authorise again or extend the authorisation lifetime.
    429 with Retry-After. Per-token limit exceeded. Wait or raise Requests per minute and token.
    The client sees zero tools. User without MCP policy, without product permissions or a client without OAuth. Check the policy, the ACL and client compatibility.
    size returns fewer rows than requested. Maximum rows per tool call reduces the size below the requested value. Raise the setting up to 50 or paginate.
    size greater than 50 returns an argument error. The schema limits size to 50. Request 50 or paginate.
    Unknown argument. The client sends a parameter that is not in the schema. Check tools/list or reference_data.
    Tickets from a group do not appear. The user's group ACL. Check the user's groups; MCP does not bypass the ACL.

    Relationship with API v2¶

    MCP and API v2 share the base, authentication, ACL and licence, but they are not the same:

    • API v2 is the way to write and to integrate in general.
    • MCP is a read-only façade for agents, with tools and schemas designed for a model.
    • An MCP OAuth token is only valid on /mcp.
    • An API v2 token is also valid on /mcp, but it is not the recommended flow for agents.
    • The API v2 OpenAPI reference includes the /mcp, /mcp/permission and OAuth routes; it is useful to generate clients and to check response codes.

    If you need to create tickets, update companies or run actions, use API v2 from chapter 11.1 with an API token and the user's permissions. MCP does not write.
