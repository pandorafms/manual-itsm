    Versiones y ciclo de soporte¶

    Pandora ITSM no se actualiza por actualizar. Cada release tiene un objetivo: una LTS prioriza que el sistema siga en pie; una FR prioriza tener antes lo nuevo. Elegir mal el canal no rompe el producto el primer día; rompe la tranquilidad del equipo cuando llega la primera incidencia.

    La tesis de este capítulo es sencilla: no busques la versión más alta, busca la que puedas defender. La última LTS es la referencia habitual para producción, pero una versión anterior bien soportada sigue siendo mejor que una última versión mal probada.

    Cómo se leen las versiones¶

    Cada instalación se describe con cuatro datos:

    Dato Ejemplo Qué es
    Versión 5.0.110 Versión del producto
    OUM 110 Release del Offline Update Manager
    MR 110 Nivel de migración de la base de datos
    Paquete 5.0.110-261001 Empaquetado y fecha de build

    La versión es la del producto. La OUM es el paquete de release que publica el Offline Update Manager. El MR es el nivel de migración de la base de datos. El paquete añade la fecha de build; no es una versión distinta.

    Desde la 105, la OUM coincide con la versión: 5.0.105 es OUM 105, 5.0.106 es OUM 106 y así hasta la 110. El MR no siempre acompaña: la 5.0.105 fue OUM 105 y MR 98; la 5.0.106 ya fue MR 106. Por eso los tres datos se miran juntos en About ITSM; ninguno sustituye a los otros.

    Un ejemplo de lectura: una instalación con versión 5.0.110, OUM 110 y MR 110 está en la release 110 y tiene la base de datos al día. Si el MR se queda atrás, el código puede ser nuevo y el esquema viejo.

    Versión LTS¶

    LTS significa Long Term Support. Es la versión de referencia para producción: se publica con menos frecuencia que las FR, se valida más y se mantiene con parches de seguridad y correcciones críticas.

    Lo que hay que tener claro:

    • Una LTS no recibe las funcionalidades nuevas de las FR. Recibe correcciones, no novedades.
    • Los parches LTS salen según necesidad, no con una cadencia fija.
    • La fecha de fin de soporte que muestra About ITSM es la de la licencia, no la de la versión. Sirve para saber si estás cubierto, no para decidir cuándo actualizar.
    • El límite real suele ponerlo el sistema operativo: si el fabricante deja de soportar EL9 o Ubuntu 22.04, la LTS más longeva se queda sin suelo firme.

    Si no hay una razón concreta para lo contrario, producción va en LTS. Y para no salirte del carril sin querer, Warp Update tiene la opción Limit to LTS updates, que descarta las versiones intermedias.

    Versión Feature Release (FR)¶

    FR significa Feature Release. Es la versión que trae funcionalidades nuevas, mejoras y correcciones con una cadencia más frecuente que la LTS.

    Tiene sentido en tres casos:

    • Necesitas una funcionalidad concreta antes de que llegue a la LTS.
    • Tienes un entorno piloto donde puedes probar sin poner en riesgo el servicio.
    • El equipo asume que hay que revisar, probar y aplicar cada release.

    Lo que no es una buena idea es tener un entorno crítico en FR sin margen de prueba. Una FR también puede recibir parches, pero lo normal es que los cambios lleguen con la siguiente FR. La novedad se prueba donde se puede volver atrás.

    Parches LTS¶

    Una LTS no se queda quieta: recibe parches. Un parche LTS corrige una vulnerabilidad, una incidencia relevante o un fallo crítico sin cambiar de familia ni traer funcionalidades nuevas.

    Los parches se identifican con la versión y el número de release que publique el fabricante; la fuente es la página oficial de actualizaciones y las notas de cada OUM. No inventes una nomenclatura propia ni mezcles un parche de FR con una LTS.

    Se aplican con Warp Update, igual que una release completa. El procedimiento está en 1.2; aquí solo importa el criterio: si es un parche LTS, va a la LTS; si es una funcionalidad nueva, va a la FR.

    Ciclo de soporte¶

    La referencia para producción es la última LTS o, con una razón justificada, la anterior todavía soportada. No hay una promesa de soporte indefinido para una LTS antigua: cuando sale una nueva, la anterior entra en la zona de planificar la actualización.

    Hay dos fechas que se confunden y conviene separar:

    • Fin de soporte de la licencia: la que muestra About ITSM. Va ligada al pago y al contrato.
    • Fin de vida de la versión: lo marca el ciclo de releases y, en la práctica, el sistema operativo.

    Antes de estirar una LTS, mira el calendario del sistema operativo y el contrato de soporte. El detalle de licencias está en 1.4; aquí basta con saber que la fecha de licencia no es la fecha de la versión.

    Compatibilidad¶

    La versión de referencia, 5.0.110, se mueve en esta ventana:

    Componente Versiones
    RHEL, Rocky Linux o AlmaLinux EL 9 y EL 10
    Ubuntu Server 22.04 y 24.04
    PHP 8.2 y 8.4
    MySQL o Percona 8.0 y 8.4, con EL10 limitado a 8.4

    La matriz completa y la instalación están en 1.1. Si tu versión actual no cumple esta ventana, el problema no se resuelve actualizando el producto: se resuelve actualizando la plataforma.

    Cómo elegir¶

    Para producción, la regla es aburrida y funciona:

    1. Mira la última LTS publicada y sus notas.
    2. Comprueba que el sistema operativo, PHP y MySQL siguen soportados.
    3. Si necesitas una funcionalidad que solo está en FR, pruébala en un piloto.
    4. Actualiza a la siguiente release o a la última, no a una combinación inventada.
    5. Verifica versión, MR, servicios, cron y logs.

    Si la FR te resuelve un problema real, adelanta la actualización, pero hazlo con copia de seguridad y ventana de mantenimiento. La estabilidad no se negocia en lo que sostiene el servicio.

    Dónde mirar¶

    • About ITSM: versión, MR y paquete de la instalación.
    • Warp journal: historial de actualizaciones aplicadas.
    • Página oficial de actualizaciones: releases publicadas y notas.
    • Notas de la OUM: qué trae y qué corrige.
    • Warp Update: LTS, parches no consecutivos y proxy.

    Actualización¶

    El procedimiento está en 1.2. Aquí queda el criterio: elige canal, comprueba compatibilidad, haz copia y actualiza. Después revisa el MR y el journal.

    Siguientes pasos¶

    • Revisa la licencia y el contrato de soporte (1.4).
    • Comprueba la matriz de compatibilidad antes de la próxima actualización.
    • Programa copias y monitorización (Parte 12).
    • Anota la versión, la OUM y el MR en el journal.
