    Proyectos y tareas¶

    Un proyecto no es una lista de tareas con colores: es un contrato de tiempo, coste y responsabilidad. Pandora ITSM permite planificar ese contrato, imputar horas contra él y comprobar si la realidad se parece a lo que se prometió. Lo demás —el Gantt, el tablero, los informes— son formas de mirar el mismo problema desde distintos ángulos.

    La idea que sostiene todo el capítulo es sencilla: un proyecto se gestiona con personas, tareas y horas, no con buenas intenciones. Si las horas no se imputan a una tarea, el coste es una ficción; si las tareas no tienen responsable, el Gantt es decoración.

    Qué es un proyecto¶

    La gestión de proyectos combina proyectos, tareas, roles y personas. Las tareas pueden tener subtareas y organizarse en estructuras jerárquicas. A su vez, una tarea puede tener tickets asociados y unidades de trabajo donde se registra el tiempo de cada persona.

    El punto de entrada es Projects → Project list. Desde ahí se crean proyectos, se consulta su estado, se filtran por grupo o tipo y se accede a la vista general.

    Un proyecto tiene un Project manager —por defecto, quien lo crea—, un grupo de proyectos, un equipo de personas con distintos roles y un conjunto de tareas. El proyecto no ejecuta el trabajo: lo ordena. Quien ejecuta son las personas y las unidades de trabajo.

    Crear un proyecto¶

    En Projects → Project list → Create project se definen los datos básicos:

    Campo Qué indica
    Name Nombre del proyecto.
    Project manager Usuario responsable. Por defecto, el creador.
    Project group Grupo lógico al que pertenece.
    CC Correo que recibe las notificaciones del proyecto.
    Start y End Fechas de inicio y fin.
    Status template Plantilla de estados de las tareas.
    Tag template Plantilla de etiquetas de las tareas.
    Company y Contract Empresa y contrato asociados, si procede.
    Description Texto descriptivo.
    Project Types Tipo de proyecto y sus campos personalizados.
    Replicate tasks from other project into this Copia las tareas de otro proyecto.

    La replicación de tareas es cómoda para proyectos que se repiten, pero copia las fechas originales: después hay que reajustar cada tarea. No es un clon con inteligencia propia.

    Un proyecto se puede asociar a una empresa o a un contrato siempre que ninguna de sus tareas esté ya asociada a una empresa o contrato, y viceversa. La restricción evita que el mismo trabajo se impute dos veces a clientes distintos.

    Vista general y edición¶

    Al hacer clic en el nombre de un proyecto se abre Project overview, la vista general. La sección Details se puede editar directamente; Quick edit permite cambiar los campos principales, como el grupo de proyectos, la plantilla de estados y la plantilla de etiquetas.

    Las pestañas principales son:

    • Task planning: planificación y lista de tareas.
    • Board view: tablero por estados.
    • Gantt chart: diagrama temporal.
    • Milestones: hitos del proyecto.
    • Edición completa: la misma interfaz de creación del proyecto.

    En la parte inferior aparecen Notes, Tracker, Attachments, Members y Budget. No son pestañas de adorno: cada una responde a una pregunta distinta sobre el proyecto.

    Estadísticas, distribución y actividad¶

    La sección Statistics resume personas implicadas, horas totales de trabajo, horas planificadas, horas facturables y duración del proyecto. Workload distribution y Task distribution muestran el reparto porcentual del trabajo y de las tareas. Activity deja ver qué ha pasado y cuándo.

    La pestaña Budget calcula la rentabilidad y compara coste estimado, coste total, importe cobrado y coste medio por hora. También desglosa el coste por rol. Si las horas no están bien imputadas, este informe será una obra de ficción con formato de tabla.

    Tracker registra las operaciones del proyecto: apertura, cierre, cambios y adiciones de información. Es el histórico que permite responder «¿quién cambió esto y cuándo?».

    Personas y roles¶

    En Members se añaden o retiran usuarios del proyecto con Add role people. Un usuario puede tener un rol global en el proyecto y otro distinto en cada tarea. Los permisos dependen del rol: desde modificación total hasta simple reporte de trabajo.

    Los roles se gestionan en People → Roles management. Pandora ITSM incluye estos roles por defecto:

    • Project manager.
    • Systems engineer.
    • Junior consultant.
    • Junior programmer.
    • Senior programmer.
    • Analyst.
    • Senior consultant.
    • Support engineer.

    El rol Project manager solo se puede editar, no borrar. Cada rol tiene un coste por hora que se usa para calcular el coste de las tareas y del proyecto. Los costes adicionales —facturas de gastos u otros cargos— se imputan directamente a la tarea.

    Tareas¶

    La planificación se hace en Project overview → Task planning. La lista muestra las tareas con su estado, fechas, progreso, horas trabajadas, desviación, prioridad y etiquetas. Se puede ordenar por cualquiera de las columnas.

    La columna Hours worked abre un resumen de las unidades de trabajo de la tarea: coste, horas, desglose y filtros por fechas, hitos o personas. La información filtrada se puede exportar a CSV.

    La columna Op. concentra las acciones:

    • Members: personas que participan en la tarea.
    • Issues: tickets asociados.
    • Work units: añadir unidades de trabajo.
    • Edit: editar la tarea.
    • Delete: borrar la tarea de forma definitiva.

    Para que las unidades de trabajo de un ticket se imputen a la tarea y al proyecto hay que asignar un rol y marcar Add to project's cost al crearlas.

    Crear y editar una tarea¶

    Con Create, al pie de la lista, se crea una tarea con sus datos básicos: nombre, prioridad, tarea padre, fechas de inicio y fin, propietario y horas estimadas. También se puede activar el envío de correo al inicio y al final, el aviso de horas extra y la recurrencia.

    La recurrencia —semanal, mensual o anual— permite llevar un contador de horas por periodo. El contador se reinicia al final de cada intervalo, pero las horas imputadas se mantienen en el total de la tarea. El intervalo de recurrencia no puede superar el total de horas.

    Después de crearla se edita para asignar personas en Add users to task, definir costes, etiquetas, prioridad, tipo de tarea y campos personalizados.

    En la edición aparecen también:

    • Estimated cost y Fixed cost: coste estimado y coste fijo.
    • Related company y Related contract/s: vínculo con empresa y contrato.
    • Progression based on hours: calcula el progreso a partir de las unidades de trabajo. Si se desactiva, mover la barra de progreso no cambia el estado de la tarea.
    • Task links: relaciones temporales con otras tareas.

    Enlaces entre tareas¶

    Los enlaces definen el orden cronológico:

    Enlace Qué impone
    Start to start Las tareas vinculadas no pueden empezar antes de que empiece esta.
    Finish to start Las tareas vinculadas no pueden empezar antes de que esta termine.
    Finish to finish Las tareas vinculadas no pueden terminar antes de que termine esta, aunque pueden terminar después.

    Seguimiento y movimiento¶

    Pandora ITSM registra apertura, cierre, cambios y adiciones de información de cada tarea, incluidas las unidades de trabajo y los ficheros adjuntos. Si una tarea se mueve de proyecto o de tarea padre, sus unidades de trabajo siguen vinculadas a ella.

    Unidades de trabajo¶

    Las unidades de trabajo de un proyecto se pueden crear desde el planificador de tareas —la opción recomendada— o desde People → Work unit → Add work unit.

    Hay dos caminos que conviene no confundir:

    • Las unidades de trabajo de un ticket imputan el tiempo del ticket cuando está asignado a una tarea, tiene rol y Add to project's cost activo.
    • Las unidades de trabajo manuales imputan directamente el tiempo introducido.

    El formulario manual permite repartir una unidad de trabajo en bloques de horas —por defecto, cuatro— hacia delante o hacia atrás en el tiempo, manteniendo el contenido y cambiando la fecha. Es útil para imputar una semana de trabajo sin crear diez registros a mano.

    Hay dos casos especiales: Work from home y las unidades de trabajo sin proyecto ni tarea. Se computan como tareas especiales dentro de un proyecto especial. Las vacaciones y las bajas tienen su propia sección en People → Work unit → Vacations and sick leave.

    Campos personalizados de tareas¶

    En Projects → Tasks types se crean tipos de tarea. Cada tipo puede tener campos personalizados numéricos, de texto, de fecha, de verdadero/falso, de lista o relacionados. Al editar una tarea se elige el tipo y aparecen sus campos.

    El funcionamiento es similar al de los campos personalizados de los tickets: sirven para clasificar, filtrar e informar. Un tipo de tarea con veinte campos que nadie rellena no mejora la planificación.

    Hitos¶

    Un hito es una tarea de duración cero que representa una fecha importante: fin de fase, entrega de un informe, revisión con el cliente. Se gestiona en Project overview → Milestones y se puede usar para filtrar informes y búsquedas.

    Los hitos admiten campos personalizados con Milestone fields:

    • Name: obligatorio; se pueden repetir nombres.
    • Field visibility: muestra el campo en la lista de hitos.
    • Type: texto, área de texto, combo o checkbox.

    Archivos adjuntos¶

    En Project overview → Attachments se pueden subir, descargar y eliminar ficheros del proyecto. Cada fichero puede llevar una descripción y se puede buscar por palabra clave, por ubicación —proyecto, tickets o unidades de trabajo— y por fecha.

    No se admiten ficheros de código fuente como .php o .pl; conviene comprimirlos antes de subirlos. Solo un administrador o el creador del fichero con permisos de administración en proyectos puede borrarlo.

    Gráfico Gantt¶

    En Project overview → Gantt chart se visualizan las tareas y su relación cronológica. Se puede abrir a pantalla completa, añadir tareas y subtareas y relacionarlas arrastrando desde el final de una tarea hasta el inicio de la siguiente.

    Las tareas no relacionadas se pueden mover de fecha. Las relacionadas tienen la restricción lógica: una no empieza antes de que termine la anterior. La opción Show real planning compara la planificación con las tareas realizadas y permite verla por mes, semana o día.

    Archivado y borrado¶

    Al terminar un proyecto se puede archivar desde Projects → Project list → Options → Archive. El proyecto pasa a la vista de archivados y conserva toda su información.

    Un proyecto archivado se puede desarchivar o borrar. Al borrarlo desaparecen sus tareas y las unidades de trabajo se quedan huérfanas: siguen existiendo, pero sin proyecto ni tarea. Los proyectos archivados no envían notificaciones automáticas de cierre de tarea, proyecto o hito.

    Para ver activos y archivados hay que abrir Filters, poner Active en Any y aplicar. El listado vuelve a los filtros por defecto al refrescarse.

    Vista de tablero¶

    Board view organiza tickets y tareas en columnas por estado. La barra horizontal inferior permite recorrer todas las columnas. La sección de filtros permite filtrar por usuarios, porcentaje realizado, etiquetas y otros valores.

    Cada columna se puede colapsar o expandir. Cada tarea tiene acciones rápidas para editar, crear una unidad de trabajo, moverla, copiarla o borrarla. Las tareas aparecen colapsadas por defecto y se pueden expandir.

    Con Ctrl se pueden seleccionar varias tareas y moverlas en bloque a otra columna. Es la forma más rápida de reorganizar un proyecto sin entrar tarea por tarea.

    Plantillas de estados¶

    En Projects → Task status templates se definen los estados de las tareas. La plantilla por defecto incluye cuatro estados —Pending, In process, Completed y Verified— con su color y visibilidad.

    La plantilla por defecto y sus cuatro estados no se pueden borrar. Al crear una plantilla nueva se copian esos cuatro estados, que tampoco se podrán borrar. Si se borra una plantilla que estaba en uso, el proyecto vuelve a la plantilla por defecto. Al cambiar un proyecto de plantilla, el estado actual se pierde y hay que asignar uno de la nueva.

    Plantillas de etiquetas¶

    En Projects → Task tag templates se definen las etiquetas de las tareas. La plantilla por defecto incluye Low, Medium y High.

    Se pueden crear plantillas por proyecto y añadir etiquetas propias. Al cambiar la plantilla de un proyecto, las etiquetas ya asignadas a las tareas se borran. Es una de esas operaciones que conviene probar en un proyecto de juguete antes de hacerla en el proyecto importante.

    Exportar a CSV¶

    La vista de tablero permite exportar las tareas seleccionadas a CSV. El fichero incluye, entre otras, estas columnas:

    ID, Project, Parent Task, Task name, Description, Completion,
Work units hours, Status, Priority, Start, End, Estimated hours,
Cost, Periodicity, Start period, Interval hours, CC, Send email,
Set hours, Involved people, Tags

    Si se accede por HTTPS, la descarga es automática; por HTTP puede hacer falta autorizar la descarga en el navegador. La exportación vuelca las tareas seleccionadas, no una copia completa del proyecto con sus estados y tickets.

    Notas¶

    La pestaña Notes guarda mensajes internos a modo de bitácora. Se pueden buscar por palabra clave y asociar a una tarea; por defecto no se asocian a ninguna.

    Las notas quedan excluidas de los informes del sistema, así que no son el lugar para registrar horas o costes. En la interfaz actual se pueden editar y borrar; no las trates como un registro inmutable.

    Reglas de flujo de trabajo¶

    En Projects → Workflow rules se definen reglas automáticas para proyectos y tareas. Son independientes de las reglas de workflow de tickets y vienen con cuatro reglas de ejemplo desactivadas.

    Cada regla tiene un modo de ejecución:

    • Cron: se evalúa periódicamente.
    • Real time: se evalúa cuando el usuario realiza una acción.

    Las condiciones se crean en la pestaña Conditions y pueden combinar campos del proyecto y de sus tareas. Por defecto la relación es OR; también se pueden usar AND, AND NOT, OR NOT y XOR. Las condiciones se pueden ordenar con Up y Down.

    Las acciones se crean en la pestaña Actions: enviar un correo a uno o varios usuarios, cambiar el administrador del proyecto, etcétera.

    Las plantillas de correo pueden usar estas macros:

    Macro Valor
    _next_milestone_ Fecha y hora del próximo hito.
    _project_completion_ Porcentaje completado del proyecto.
    _project_cost_deviation_ Desviación del coste del proyecto.
    _project_costs_ Coste del proyecto.
    _project_end_date_ Fecha de fin del proyecto.
    _project_estimated_costs_ Coste estimado del proyecto.
    _project_estimated_hours_ Horas estimadas del proyecto.
    _project_manager_ Administrador del proyecto.
    _project_name_ Nombre del proyecto.
    _project_pending_hours_ Horas pendientes del proyecto.
    _project_start_date_ Fecha de inicio del proyecto.
    _project_used_hours_ Horas trabajadas del proyecto.
    _project_users_ Usuarios implicados en el proyecto.
    _task_completion_ Porcentaje completado de la tarea.
    _task_end_date_ Fecha de fin de la tarea.
    _task_estimated_hours_ Horas estimadas de la tarea.
    _task_name_ Nombre de la tarea.
    _task_pending_hours_ Horas pendientes de la tarea.
    _task_recurrence_ Periodicidad de la tarea.
    _task_start_date_ Fecha de inicio de la tarea.
    _task_used_hours_ Horas trabajadas de la tarea.
    _task_users_ Usuarios implicados en la tarea.
    _workflow_content_ Resumen de horas, periodicidad y otros datos.

    Grupos y tipos de proyecto¶

    Los Project groups se gestionan en Projects → Project groups. Sirven para agrupar proyectos que comparten características. El nombre puede repetirse y el icono es opcional. Después se asigna cada proyecto a su grupo y se puede filtrar por él en la lista.

    Los Projects types se gestionan en Projects → Projects types. Un tipo de proyecto puede tener campos personalizados de texto, numéricos, fecha, verdadero o falso, listas, listas relacionadas jerárquicamente y URL con descripción. Esos campos se pueden filtrar en la lista de proyectos.

    Cada campo personalizado de tipo de proyecto tiene tres opciones comunes:

    • Show in the projects list: lo muestra como columna en la lista.
    • Global field: lo añade a todos los tipos existentes y futuros.
    • Required: obliga a asignar un valor.

    Cuidado con los campos globales: una vez creados solo se pueden borrar, no editar. Si además se marcan como Show in the projects list, aparecerán tantas columnas como tipos de proyecto existan. Un proyecto sin tipo asignado usa el primero de la lista al editarlo, así que conviene revisar el tipo antes de guardar.

    Buenas prácticas¶

    • Define un responsable claro y un grupo de proyecto desde el principio.
    • Asigna roles y costes antes de imputar horas.
    • Usa tipos y campos personalizados solo si se van a filtrar o informar.
    • Mantén las estimaciones y las horas reales actualizadas.
    • Usa hitos para las fechas que de verdad importan.
    • Archiva los proyectos terminados en lugar de borrarlos.
    • Revisa las plantillas de estados y etiquetas antes de cambiarlas.
    • Consulta los informes de proyectos después de imputar horas, no antes de que existan.
