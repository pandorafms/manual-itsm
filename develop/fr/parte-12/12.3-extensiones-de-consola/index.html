    Extensions de console¶

    Les extensions de console ajoutent des pages, des onglets et des entrées de menu sans modifier le cœur de Pandora ITSM. Elles se gèrent dans Setup → Console extensions : on y télécharge le modèle d'exemple, on envoie une extension, on l'active ou la désactive, on remplace le paquet et on le supprime.

    Seules les extensions enregistrées comme gérées et actives s'exécutent. Le code copié à la main dans extensions/ ou enterprise/extensions/ n'est plus chargé : pour migrer une ancienne extension, envoyez-la via le gestionnaire. Les extensions sont stockées dans extensions/ et enregistrées dans textension. Les mêmes opérations sont disponibles via l'API v2 dans /extension.

    Format d'une extension¶

    Une extension s'envoie comme un seul fichier .php ou comme un .zip. Le ZIP doit contenir un index.php à la racine ; le reste des fichiers est facultatif.

    Exigences du paquet :

    • index.php à la racine du ZIP.
    • Fichiers .php et assets statiques : .js, .css, .json, images (png, jpg, jpeg, gif, webp, ico, svg), polices (woff, woff2, ttf), .txt et .map.
    • Chemins relatifs sûrs, sans .., avec une profondeur maximale de 16 niveaux.
    • Jusqu'à 256 entrées, 10 Mo de ZIP, 32 Mo expansés et 8 Mo par fichier.
    • Pas de dossier data/ : il est réservé aux données d'exécution de l'extension.
    • Le code PHP doit déclarer une paire de hooks de niveau supérieur :
    • extensions_add_side_menu_option avec extensions_add_main_function, pour une page d'Operation.
    • extensions_add_godmode_side_menu_option avec extensions_add_godmode_function, pour une page de Godmode.
    • extensions_add_tab_option avec extensions_add_tab_function, pour un onglet de ticket.

    Le callback du hook doit être une fonction locale nommée ou une closure inline. L'extension peut inclure un README.txt avec les instructions et un index.php comme point d'entrée. Le modèle téléchargé depuis le gestionnaire inclut un exemple fonctionnel et explique la structure dans son propre README.txt.

    Installation, activation et remplacement¶

    Une extension s'installe depuis Setup → Console extensions avec Upload extension : on choisit le fichier .php ou .zip, on lui donne un nom et on décide s'il reste activé. L'envoi crée le fichier ou le dossier dans extensions/ et l'enregistre comme géré.

    Mettre à jour une extension n'oblige plus à la supprimer et à la réinstaller. Si l'on envoie un paquet portant le même nom de fichier qu'une extension installée, la console signale qu'elle est déjà installée et demande confirmation dans la boîte de dialogue Update extension (Update pour continuer, Cancel pour abandonner). La confirmation remplace le paquet sans toucher aux données. La même mise à jour peut se faire depuis l'édition de l'extension, en remplaçant le fichier par un autre du même nom. Le nom de fichier est l'identité de l'extension, pas une étiquette décorative : il est comparé sans tenir compte des majuscules et des minuscules, et ne compte que si l'extension précédente est gérée.

    Dans les extensions conditionnées en ZIP, les données persistantes résident dans le dossier data/ de l'extension elle-même. Ce dossier est le seul qui survive au remplacement : le nouveau paquet remplace entièrement le précédent, supprime les fichiers absents du ZIP et déplace data/ tel quel dans le nouveau paquet. Si la mise à jour échoue, l'extension précédente et ses données restent en l'état.

    data/ est un dossier réservé. Un ZIP qui l'inclut à la racine est rejeté : ce dossier n'existe que pour les données d'exécution de l'extension, et le paquet ne peut pas le contenir. Ainsi, une mise à jour n'écrase jamais de données réelles. Il n'est pas non plus servi par URL, même lorsqu'il contient du JSON ou du TXT : les fichiers chargés par l'interface vont dans un autre dossier du paquet. La suppression de l'extension supprime aussi ses données, comme auparavant.

    Pour que les données survivent, le code de l'extension doit les écrire dans __DIR__.'/data' et créer le dossier la première fois avec mkdir($dir, 0700). Tout autre fichier écrit hors de data/ est perdu à la mise à jour suivante. S'il a besoin de valeurs initiales, il peut les inclure dans un autre dossier du ZIP, par exemple defaults/, et les copier dans data/ uniquement lorsqu'elles n'existent pas. Si les données sont des enregistrements de l'application, il est préférable de les stocker dans la base de données au moyen des services de l'application. Une extension d'un seul .php n'a pas de dossier propre : si elle a besoin de persistance, il faut la conditionner en ZIP.

    Dans l'API v2, POST /extension accepte le champ replace=true pour mettre à jour une extension installée avec le même comportement. Sans ce champ, la réponse reste une erreur 400, donc les intégrations actuelles ne changent pas.

    Sécurité et portée¶

    Le code d'une extension s'exécute avec les permissions du serveur : ce n'est pas un bac à sable. Installez uniquement vos propres extensions ou des extensions vérifiées, et gardez à l'esprit qu'un paquet peut contenir des pages d'Operation, des pages de Godmode, des onglets de ticket, des assets et des hooks de menu. Une extension désactivée n'est pas chargée, mais ses fichiers restent sur le serveur jusqu'à sa suppression.

    Une extension n'hérite pas automatiquement de l'ACL de la section du menu où elle apparaît. Il est important que l'extension elle-même vérifie les bits d'accès du profil qui doivent permettre de la consulter et de l'utiliser ; sinon, tout utilisateur qui atteint la page pourrait l'exécuter. Sa place dans le menu organise, elle ne protège pas : l'ACL se contrôle dans l'extension, en plus de la section où elle se trouve.
