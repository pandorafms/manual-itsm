    MCP (Model Context Protocol)¶

    Pandora ITSM publica un servidor MCP para que un agente de IA pueda consultar tickets, empresas, contactos, oportunidades, notas, correo, agenda y web tracking sin salir de la consola. No es un chatbot: es una capa de lectura que habla el protocolo estándar de los clientes MCP y que se autentica con OAuth 2.1.

    La idea es sencilla: el agente deja de copiar y pegar datos de la consola y pregunta directamente. El servidor responde con las mismas ACL, la misma auditoría y los mismos límites que la API v2. La diferencia es el interlocutor, que ahora es un modelo y no un script.

    Este capítulo cubre el servidor MCP de Pandora ITSM: qué herramientas expone, cómo se activa, cómo se autentica un cliente, qué devuelve cada herramienta y dónde se corta el acceso. La API v2 sigue siendo la vía para escribir y para integrar aplicaciones; el MCP es una fachada de solo lectura para agentes.

    Qué es y qué permite¶

    MCP (Model Context Protocol) es un protocolo abierto para que un cliente (Claude Code, Cursor, OpenCode, Codex, un conector web) descubra herramientas y las ejecute contra un servidor. Pandora ITSM implementa la parte de servidor sobre HTTP, con JSON-RPC 2.0 y autenticación OAuth 2.1.

    Un servidor de solo lectura¶

    Todas las herramientas del catálogo declaran readOnlyHint: true. El servidor no crea, modifica ni borra tickets, empresas ni ningún otro objeto. Tampoco adjunta ficheros ni envía correo. Si el agente necesita escribir, tendrá que usar la API v2 con un token de API y las ACL correspondientes.

    El catálogo se agrupa en siete áreas:

    Área Herramientas Para qué
    Empresas company_search, company_get, activity_feed Buscar cuentas, leer su ficha y ver su actividad reciente.
    Tickets ticket_search, ticket_get Localizar tickets y leer su estado, descripción, seguimiento y unidades de trabajo.
    Contactos contact_search, contact_get Buscar personas de una empresa y leer su ficha.
    Oportunidades deal_search, deal_get Consultar el embudo, la previsión y el detalle de una oportunidad.
    Notas, correo y agenda note_list, email_list, schedule_list Leer notas, metadatos de correo y tareas, reuniones o recordatorios.
    Web tracking webtracking_summary Contar contactos atribuidos por origen, categoría, campaña o mes.
    Referencia reference_data Traducir identificadores y enumeraciones, y descubrir filtros permitidos.

    Qué puedes preguntar¶

    Algunos ejemplos reales de lo que un agente puede resolver con estas herramientas:

    • «¿En qué estado está el ticket 4321 y qué ha pasado en las últimas respuestas?»
    • «Resume la actividad de la empresa Acme en la última semana.»
    • «¿Qué oportunidades ha movido el comercial jlopez este trimestre y cuál es la previsión ponderada?»
    • «¿Cuántos contactos atribuidos a Google Ads han llegado este mes?»
    • «Dame los tickets cerrados del grupo Soporte entre el 1 y el 15 de noviembre.»

    El agente encadena búsquedas y lecturas: primero resuelve identificadores con reference_data, después busca con *_search y por último abre el detalle con *_get.

    Lo que no hace¶

    • No escribe. No hay herramientas de creación, actualización ni borrado.
    • No devuelve cuerpos de correo ni destinatarios; solo metadatos.
    • No devuelve correo ni teléfono en las búsquedas de empresas y contactos. Para obtenerlos hay que pedir el detalle de un contacto concreto.
    • No sustituye a la API v2 ni a la consola. Es una vista de lectura para agentes.
    • No comparte tokens con la API v2: un token OAuth emitido para MCP solo vale en /mcp.

    Requisitos¶

    Requisito Detalle
    HTTPS Los clientes MCP en la nube exigen HTTPS. Los redirects OAuth solo admiten HTTPS o loopback HTTP (localhost, 127.0.0.1, [::1]).
    URL pública Public MCP URL debe ser una URL absoluta HTTPS terminada en /mcp. Sin ella no se puede activar MCP ni publicar los metadatos OAuth.
    ACL de la API La lista List of IP with access to API (api_acl) se aplica también a /mcp y a los endpoints OAuth. Debe incluir las IP de salida de los clientes. Con clientes en la nube, añade sus rangos o abre la lista a *; el control real pasa a ser la política MCP y OAuth.
    Usuario y permisos El usuario que autoriza el acceso debe estar activo, incluido en la política MCP y tener los permisos de producto que exige cada herramienta.
    Cliente compatible El cliente debe soportar servidores MCP remotos por HTTP y OAuth 2.1 con registro dinámico y PKCE.

    Activación y configuración¶

    La configuración vive en Setup → Setup → MCP setup. Solo los administradores pueden abrirla y guardarla. La página se organiza en pestañas: Status, Discovery, Connect, Access policy, Runtime settings y Authorizations.

    El interruptor general¶

    Enable MCP server enciende o apaga el servidor. Mientras está apagado, el endpoint responde con un error de política y los clientes no pueden usar ninguna herramienta. Al activarlo, la página muestra el resto de pestañas y la guía de inicio:

    1. Activar MCP.
    2. Elegir quién puede usarlo y configurar la URL pública.
    3. Revisar la ACL de la API.
    4. Conectar el cliente; la primera conexión abre la página de consentimiento.

    No se puede activar MCP sin Public MCP URL. El servidor necesita una URL de confianza para construir el emisor OAuth y los documentos de descubrimiento, y nunca los deriva de la cabecera Host.

    Estado y lista de comprobación¶

    La pestaña Status muestra el endpoint y cinco comprobaciones:

    Comprobación Qué significa
    MCP enabled El interruptor general está activo.
    Access policy Hay al menos un usuario o grupo permitido, o la política permite a todos.
    HTTPS La consola se sirve por HTTPS.
    Public MCP URL La URL pública está configurada.
    API ACL La ACL de la API no está restringida a 127.0.0.1 o localhost.

    Un punto rojo no bloquea necesariamente el guardado, pero sí explica por qué un cliente no conecta. La comprobación de API ACL es la que más se olvida: si la lista solo permite loopback, un cliente que llega desde otra IP recibe 401 antes de que empiece el baile OAuth.

    Descubrimiento OAuth¶

    La pestaña Discovery muestra las dos URL que un cliente consulta antes de autenticarse:

    https://<host>/.well-known/oauth-protected-resource
https://<host>/.well-known/oauth-authorization-server

    Ambos documentos deben publicarse en la raíz del dominio. Si Pandora ITSM vive en un subdirectorio o detrás de un proxy, el servidor web debe reescribir o alinear esas rutas; en ese caso la URL de descubrimiento añade la ruta del recurso. La pestaña Discovery muestra las dos URL exactas de la instalación e incluye un botón Check que lanza una petición real y marca el resultado.

    Configuración de Apache¶

    Los documentos los sirve la API v2 en /pandoraitsm/api/v2/.well-known/..., pero el cliente los busca en la raíz del dominio. Hay que reescribir esas rutas en el virtual host HTTPS. Añade las reglas a tu virtual host de 443; el bloque siguiente muestra el contexto mínimo. Con la instalación en /pandoraitsm y la URL pública https://itsm.example.com/pandoraitsm/api/v2/mcp:

    <VirtualHost *:443>
    ServerName itsm.example.com
    DocumentRoot /var/www/html

    RewriteEngine On

    # Recurso protegido (RFC 9728)
    RewriteRule ^/\.well-known/oauth-protected-resource/pandoraitsm/api/v2/mcp$ \
        /pandoraitsm/api/v2/.well-known/oauth-protected-resource [PT,L]

    # Servidor de autorización (RFC 8414)
    RewriteRule ^/\.well-known/oauth-authorization-server/pandoraitsm/api/v2$ \
        /pandoraitsm/api/v2/.well-known/oauth-authorization-server [PT,L]

    # Fallback si el cliente pide la raíz sin la ruta del recurso
    RewriteRule ^/\.well-known/oauth-protected-resource$ \
        /pandoraitsm/api/v2/.well-known/oauth-protected-resource [PT,L]

    RewriteRule ^/\.well-known/oauth-authorization-server$ \
        /pandoraitsm/api/v2/.well-known/oauth-authorization-server [PT,L]
</VirtualHost>

    Sustituye pandoraitsm por el directorio real de la consola. Si la instalación está en la raíz, cambia /pandoraitsm/api/v2 por /api/v2 y elimina pandoraitsm de las rutas. Las dos primeras reglas atienden la ruta canónica con el path del recurso; las dos últimas cubren a los clientes que piden solo /.well-known/.... El [PT,L] deja que Apache pase la petición al front controller de la API sin cambiar la URL que ve el cliente.

    Asegúrate de que mod_rewrite está activo y de que las reglas están en el virtual host de 443, no en un .htaccess (si las pones en .htaccess, quita la barra inicial de los patrones). Después recarga Apache:

    # RHEL, AlmaLinux, Rocky Linux
sudo systemctl reload httpd

# Debian, Ubuntu
sudo systemctl reload apache2

    Comprueba las dos URL desde una IP autorizada en api_acl:

    curl -s https://itsm.example.com/.well-known/oauth-protected-resource | python3 -m json.tool
curl -s https://itsm.example.com/.well-known/oauth-authorization-server | python3 -m json.tool

    La primera debe devolver resource con la URL pública y authorization_servers; la segunda, issuer y los endpoints. Si recibes el HTML de la consola o un 404, la regla no está entrando: revisa el ServerName, el DocumentRoot y que mod_rewrite esté cargado. Si delante hay un proxy inverso, debe reenviar /.well-known/oauth-* a este Apache.

    El documento de recurso protegido declara el recurso, el emisor y el permiso itsm.read. El documento del servidor de autorización declara los endpoints de autorización, token, registro y revocación, el flujo authorization_code, el refresco, PKCE S256 y el método de autenticación de cliente none.

    Política de acceso¶

    La pestaña Access policy decide qué usuarios pueden usar MCP. Hay cuatro listas y dos conmutadores de recursión:

    • Allowed users y Blocked users.
    • Allowed groups y Blocked groups.
    • Include child groups for allowed groups.
    • Include child groups for blocked groups.

    La evaluación es acumulativa y el bloqueo gana:

    1. Si MCP está desactivado, se deniega todo.
    2. Si el usuario está desactivado, se deniega.
    3. Si el usuario está en Blocked users, se deniega.
    4. Si el usuario pertenece a un grupo bloqueado, se deniega.
    5. Si la política permite a todos los usuarios o a todos los grupos, o el usuario está en Allowed users, se permite.
    6. Si el usuario pertenece a un grupo permitido, se permite.
    7. En cualquier otro caso, se deniega.

    La interfaz ya no muestra los interruptores «permitir a todos»; la API los mantiene por compatibilidad. Si se activan por API, la política resultante permite a todos y las listas de bloqueo siguen teniendo prioridad.

    Ajustes de ejecución¶

    La pestaña Runtime settings controla el comportamiento del servidor:

    Ajuste Qué hace Valor por defecto Rango
    Maximum rows per tool call Limita cuántas filas puede devolver una herramienta en una sola llamada. El esquema de cada herramienta ya permite hasta 50; este ajuste puede reducirlo. Si el cliente pide más filas de las permitidas, se queda en el valor configurado. 50 1–50
    Requests per minute and token Fija cuántas peticiones puede hacer cada token en un minuto. Al superarlo, la respuesta es 429 con Retry-After. 0 desactiva el límite. 60 0–1000
    Audit retention (days) Decide cuántos días se conservan las llamadas en la auditoría antes de purgarse. 90 1–3650
    Public MCP URL Es la URL pública del endpoint. Se usa para construir el emisor OAuth y los documentos de descubrimiento; sin ella no se puede activar MCP. Debe ser HTTPS y terminar en /mcp. vacío URL HTTPS
    Authorization lifetime (days, 0 = unlimited) Marca la vida máxima de una autorización desde que el usuario aprueba el consentimiento. Al cumplirse, el cliente debe volver a autorizar. 0 la hace ilimitada. 90 0–3650
    Allowed redirect hosts Decide a qué hosts puede redirigir un cliente tras el consentimiento. Un host por línea; *.ejemplo.com incluye subdominios; vacío permite cualquiera. claude.ai, chatgpt.com, localhost, 127.0.0.1 Hasta 50

    Public MCP URL no admite credenciales, query string ni fragmento. Si la instalación está detrás de un proxy, la URL debe ser la que ve el cliente, no la URL interna del servidor.

    Autorizaciones¶

    La pestaña Authorizations lista las aplicaciones que cada usuario ha autorizado: nombre del cliente, hosts de redirección, usuario, última IP, fecha de autorización, último uso, caducidad y botón para revocar. Revocar una autorización elimina los tokens de ese usuario para ese cliente; no afecta a otros usuarios del mismo cliente.

    Cada usuario puede ver y revocar sus propias autorizaciones desde la pestaña MCP applications de su ficha de usuario.

    Configurar por API¶

    La política también se puede leer y escribir con la API v2, usando un token de administrador. Estos endpoints no aceptan tokens OAuth de MCP.

    GET /api/v2/mcp/permission
PUT /api/v2/mcp/permission

    El PUT acepta los campos de la política y deja intactos los que se omiten:

    {
  "enabled": true,
  "allowedUsers": ["admin", "soporte"],
  "blockedUsers": ["temporal"],
  "allowedGroups": [1, 26],
  "blockedGroups": [],
  "allUsersAllowed": false,
  "allGroupsAllowed": false,
  "allowedGroupsRecursion": true,
  "blockedGroupsRecursion": false
}

    La respuesta devuelve la política guardada. Un 400 indica un valor inválido; un 403, que el token no pertenece a un administrador.

    Conectar un cliente MCP¶

    La pestaña Connect ofrece la URL, un prompt listo para pegar en el agente y la alternativa para chats web. El prompt está en inglés porque lo consume el agente, no el usuario.

    El prompt para el agente¶

    Connect yourself to the Pandora ITSM MCP server.

Server
- Name: itsm
- Transport: Streamable HTTP (remote MCP server)
- URL: https://itsm.example.com/pandoraitsm/api/v2/mcp
- Authentication: OAuth 2.1 with dynamic client registration and PKCE. The server publishes
  its metadata under /.well-known/oauth-protected-resource. Do not ask me for an API key or
  a client secret.

Steps
1. Identify which MCP client you are (Claude Code, Cursor, OpenCode, Codex, VS Code...) and add
   the server with that client's official method: its CLI command if it has one, otherwise its
   MCP configuration file. Use the user-level scope unless I say otherwise.
2. Keep the existing configuration: add or update only the "itsm" entry, and show me the change
   before writing any file.
3. Start the authorization (for example, /mcp in Claude Code). A Pandora ITSM page opens in the
   browser: I will sign in and approve the access myself. Never ask for my password.
4. Once connected, list the available tools and show them to me. They are read-only.

If the URL is not reachable or its certificate is not trusted, stop and tell me the exact error.
Do not disable TLS verification. If you cannot configure MCP servers yourself (for example, a web
chat), tell me to add a custom connector with the URL above instead.

    OpenCode¶

    OpenCode añade el servidor con su CLI y guarda la configuración en el ámbito de usuario:

    opencode mcp add itsm --url https://itsm.example.com/pandoraitsm/api/v2/mcp --global
opencode mcp list

    Después, en la interfaz, abre /mcps, selecciona itsm y completa la autorización en el navegador.

    Claude Code¶

    claude mcp add --transport http itsm https://itsm.example.com/pandoraitsm/api/v2/mcp --scope user
claude mcp list

    Dentro de Claude Code, /mcp muestra el servidor y permite iniciar sesión. El token se guarda y se refresca solo.

    Cursor y otros clientes con fichero de configuración¶

    Muchos clientes leen una entrada mcpServers con la URL del servidor:

    {
  "mcpServers": {
    "itsm": {
      "type": "http",
      "url": "https://itsm.example.com/pandoraitsm/api/v2/mcp"
    }
  }
}

    El nombre exacto del campo de transporte cambia entre clientes (type, transport, streamable-http). Si el cliente no admite servidores remotos por HTTP o no sabe hacer OAuth con registro dinámico, no podrá conectarse: usa el prompt del agente o un cliente compatible.

    Claude.ai y ChatGPT¶

    Los chats web no pueden configurarse solos. En Settings → Connectors → Add custom connector se pega la URL pública del servidor y se completa el consentimiento. La aplicación aparecerá después en la lista de autorizaciones.

    Comprobar la conexión¶

    Una conexión correcta devuelve el catálogo de 14 herramientas con tools/list. Si el cliente muestra cero herramientas, revisa en este orden: URL, certificado, ACL de la API, Public MCP URL, política MCP y permisos del usuario.

    Cómo se llama una herramienta¶

    {
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "ticket_search",
    "arguments": {
      "freeSearch": "impresora",
      "status": "ASSIGNED",
      "size": 10
    }
  }
}

    Los argumentos deben ser un objeto. Un nombre de herramienta desconocido devuelve -32601; un argumento que no está en el esquema devuelve -32602/isError.

    Parámetros comunes¶

    Solo las herramientas de listado comparten estos parámetros. *_get no pagina ni ordena.

    Paginación¶

    Parámetro Tipo Por defecto Qué hace
    page entero ≥ 0 0 Página, empezando por cero.
    size entero 1–50 20 Filas por página. webtracking_summary usa 50 por defecto.

    La respuesta incluye:

    {
  "pagination": {
    "total": 3252,
    "page": 0,
    "size": 20,
    "totalPages": 163,
    "nextPage": 1
  }
}

    nextPage es null en la última página. Maximum rows per tool call reduce size por debajo del máximo de 50 que permite el esquema.

    Ordenación¶

    Parámetro Tipo Qué hace
    sortField cadena Campo de ordenación. Cada herramienta publica su lista.
    sortDirection ascending o descending Sentido de la ordenación.
    sortMultipleFields objeto Hasta tres campos con su sentido. No se combina con sortField/sortDirection.

    Ejemplo:

    {
  "sortMultipleFields": {
    "priority": "descending",
    "startDate": "ascending"
  }
}

    Filtros genéricos¶

    Las herramientas de empresas, contactos, oportunidades, agenda, notas, correo y actividad aceptan fieldConditions: hasta 10 condiciones sobre columnas reales. No se admite jsonPath ni alias derivados.

    {
  "fieldConditions": [
    { "field": "createdAt", "operator": ">=", "value": "2026-01-01" },
    { "field": "country", "operator": "in", "value": ["ES", "FR"] }
  ]
}

    Operadores admitidos:

    Operador Uso
    =, !=, <>, >, <, >=, <= Comparación simple.
    like, not_like Coincidencia de texto.
    in, not_in Lista de hasta 50 valores.
    between, not_between Rango de dos valores.
    is_null, is_not_null Nulo o no nulo.
    is_empty, is_not_empty Vacío o no vacío.

    ticket_search no admite fieldConditions; usa sus filtros con nombre (status, priority, idGroup, idUser, fechas). Para saber qué campos y operadores acepta cada herramienta, llama a reference_data con types: ["filter_fields"].

    Fechas¶

    Las fechas se envían como YYYY-MM-DD. El servidor también acepta una fecha y hora ISO 8601 y se queda con la fecha. En los rangos, el límite superior incluye el día completo cuando la herramienta así lo declara (createdTo, lastActivityTo). Una fecha inválida devuelve isError con el nombre del campo.

    Identificadores y referencia¶

    Los identificadores son los de la consola. No se inventan ni se deducen del nombre. Antes de filtrar por estado, prioridad, grupo, pipeline o etapa, pide las tablas a reference_data:

    {
  "jsonrpc": "2.0",
  "id": 4,
  "method": "tools/call",
  "params": {
    "name": "reference_data",
    "arguments": {
      "types": ["ticket_statuses", "ticket_priorities", "groups"]
    }
  }
}

    Permisos, auditoría y límites¶

    Política MCP y ACL del producto¶

    La política MCP decide quién puede entrar. Después, cada herramienta aplica la ACL del producto:

    Herramienta Permiso que se comprueba
    company_search CR
    company_get CM
    activity_feed CR
    ticket_search ACL de grupos de la lista de tickets.
    ticket_get IR más la ACL de grupos del ticket.
    deal_search CR
    deal_get CR
    contact_search CM
    contact_get CM
    note_list CR
    email_list CR
    schedule_list CRM
    webtracking_summary CM
    reference_data CR

    Un usuario con MCP permitido pero sin el permiso de producto recibe un tools/call con isError: true y el mensaje de ACL. No hay forma de saltarse la ACL de grupos de tickets: el listado y el detalle la aplican.

    Límite de peticiones¶

    El límite es por token y minuto. Por defecto, 60 peticiones por minuto. Se cuentan todas las llamadas, no solo tools/call. Al superarlo, la respuesta es 429 con Retry-After y un error JSON-RPC -32002.

    El contador se guarda en tmcp_rate_limit y se limpia de forma oportunista. Un valor 0 desactiva el límite; no lo hagas en una instalación expuesta.

    Auditoría¶

    Cada llamada a una herramienta se registra en tmcp_audit con:

    Campo Contenido
    id_user Usuario que autorizó el token.
    token_uuid UUID del token.
    tool Nombre de la herramienta.
    arguments Argumentos, con secretos redactados y textos largos recortados.
    rows_returned Filas devueltas.
    duration_ms Duración.
    status ok, error o denied.
    error_code, error_message Motivo del fallo, si lo hubo.
    ip IP de origen.
    mcp_session Identificador de la petición.
    created_at Fecha.

    Los argumentos se redactan si la clave contiene pass, token, secret, authorization, cookie o session; los textos se cortan a 500 caracteres y la estructura a tres niveles y 50 claves. Las llamadas a herramientas denegadas o limitadas también se registran.

    Los administradores pueden ver las llamadas en Setup → Audit log → MCP, una pestaña que solo aparece cuando MCP está activo. La retención por defecto es de 90 días.

    Privacidad y truncado¶

    Herramienta Qué se recorta
    company_search, contact_search No devuelven correo ni teléfono.
    contact_get Con detail=true devuelve correo, teléfono y móvil.
    email_list No devuelve cuerpo ni destinatarios.
    ticket_get Descripción y epílogo a 4000 caracteres; seguimiento y unidades de trabajo a 2000.
    note_list Texto a 1000 caracteres.
    schedule_list Descripción a 1000 caracteres.

    Estos límites no son configurables por herramienta. El objetivo es que un agente no vuelque media base de datos en el contexto del modelo.

    Problemas frecuentes¶

    Síntoma Causa probable Solución
    El cliente no descubre OAuth (404 en /.well-known/...). Los documentos no se publican en la raíz del dominio o el proxy no los reescribe. Revisar la pestaña Discovery y el rewrite del servidor web.
    401 antes de abrir el navegador. La IP del cliente no está en api_acl. Añadir la IP o el rango en Setup → Setup → General setup.
    403 al activar MCP. Falta Public MCP URL o la licencia no es válida. Configurar la URL HTTPS terminada en /mcp y revisar la licencia.
    503 en los metadatos. Public MCP URL vacía. Configurarla; el emisor OAuth no se deriva del Host.
    El consentimiento se repite cada poco. La autorización caducó (ajuste Authorization lifetime) o el refresco falló. Volver a autorizar o ampliar la vida de la autorización.
    429 con Retry-After. Límite por token superado. Esperar o subir Requests per minute and token.
    El cliente ve cero herramientas. Usuario sin política MCP, sin permisos de producto o cliente sin OAuth. Revisar política, ACL y compatibilidad del cliente.
    size devuelve menos filas de las pedidas. Maximum rows per tool call reduce el tamaño por debajo de lo solicitado. Subir el ajuste hasta 50 o paginar.
    size mayor de 50 devuelve un error de argumento. El esquema limita size a 50. Pedir 50 o paginar.
    Unknown argument. El cliente envía un parámetro que no está en el esquema. Consultar tools/list o reference_data.
    Los tickets de un grupo no aparecen. ACL de grupos del usuario. Revisar los grupos del usuario; MCP no salta la ACL.

    Relación con la API v2¶

    MCP y la API v2 comparten base, autenticación, ACL y licencia, pero no son lo mismo:

    • La API v2 es la vía de escritura y de integración general.
    • MCP es una fachada de lectura para agentes, con herramientas y esquemas pensados para un modelo.
    • Un token OAuth de MCP solo vale en /mcp.
    • Un token de API v2 vale también en /mcp, pero no es el flujo recomendado para agentes.
    • La referencia OpenAPI de la API v2 incluye las rutas /mcp, /mcp/permission y los endpoints OAuth; sirve para generar clientes y para comprobar los códigos de respuesta.

    Si necesitas crear tickets, actualizar empresas o lanzar acciones, usa la API v2 del capítulo 11.1 con un token de API y los permisos del usuario. El MCP no escribe.
