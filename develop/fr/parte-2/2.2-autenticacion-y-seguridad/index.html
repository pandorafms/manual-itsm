    Authentification et sécurité¶

    S'authentifier ne consiste pas à remplir un formulaire : c'est prouver qui vous êtes avant que le produit ne vous laisse faire quoi que ce soit. Dans Pandora ITSM, cette porte peut rester à la maison, être déléguée à un annuaire ou être partagée avec Pandora FMS. Choisir la mauvaise méthode ne casse pas la console le premier jour ; elle la laisse ouverte ou enferme dehors quelqu'un qui devrait entrer.

    La thèse de ce chapitre est simple : l'authentification se configure une fois et se révise à chaque changement d'organisation. Un annuaire qui n'existe plus, une politique de mots de passe que personne ne se rappelle et un 2FA qui dépend du courriel sont des façons très efficaces de s'enfermer dehors de son propre outil.

    Comment entrer dans Pandora ITSM¶

    L'accès comporte deux couches qu'il ne faut pas mélanger :

    • Authentification : qui vous êtes. La méthode configurée la résout.
    • Autorisation : ce que vous pouvez faire. Les groupes et profils de 2.1 la résolvent.

    Un utilisateur peut s'authentifier correctement et n'avoir aucune permission. Ou l'inverse : avoir un profil énorme et ne pas pouvoir entrer parce que son annuaire ne répond pas. La première couche est ici ; la seconde est en 2.1.

    Les superadministrateurs sont l'exception : ils s'authentifient toujours localement dans Pandora ITSM, même si le reste des utilisateurs passe par AD, LDAP ou Pandora FMS. C'est une décision volontaire pour qu'une panne d'annuaire ne laisse pas le produit sans clé maîtresse.

    Méthode d'authentification¶

    La configuration se trouve dans Setup → Setup → Authentication configuration.

    Méthode Ce qu'elle utilise Quand elle a du sens
    Local Pandora ITSM Utilisateurs et mots de passe dans la base Petites installations ou absence d'annuaire central
    LDAP Annuaire LDAP standard Organisations avec OpenLDAP, 389 Directory Server, etc.
    Active Directory Microsoft AD Entreprises avec comptes et groupes dans AD
    Pandora FMS API v2 d'un serveur PFMS Environnements qui centralisent déjà les utilisateurs dans Pandora FMS

    Pandora ITSM interroge d'abord la méthode distante configurée. Si l'utilisateur existe et que le mot de passe est correct, il entre ; en cas d'échec, il peut utiliser l'authentification locale seulement si le fallback est activé.

    Authentification locale¶

    C'est l'option par défaut et la plus simple : les utilisateurs vivent dans tusuario et le mot de passe est vérifié dans la base.

    • La création et la modification se font dans People → User management (2.1).
    • La politique de mots de passe s'applique ici.
    • La récupération de mot de passe envoie un lien par courriel ; elle nécessite donc un SMTP opérationnel.
    • Les superadministrateurs utilisent toujours cette voie.

    Pour une petite installation, c'est suffisant. Pour une organisation dotée d'un annuaire, dupliquer les utilisateurs à deux endroits finit souvent en comptes orphelins.

    Active Directory¶

    Déléguer à Microsoft Active Directory centralise les comptes et les identifiants. Pandora ITSM a toujours besoin du profil et du groupe : AD dit qui vous êtes ; ITSM décide ce que vous pouvez faire.

    Champs de connexion :

    Champ Ce qu'il indique
    Active directory server Hôte ou IP du contrôleur de domaine
    Active directory port Port, généralement 389 ou 636
    Domain Domaine AD
    Start TLS Chiffre la connexion avec TLS

    Options importantes :

    • Fallback to local authentication : si AD échoue, permet de se connecter avec le mot de passe local. Utile comme filet de sécurité ; aussi une porte à surveiller.
    • Advanced Configuration AD : associe les groupes AD aux profils et groupes de Pandora ITSM. C'est ainsi qu'un utilisateur AD hérite du bon profil.
    • Automatically create remote users : crée l'utilisateur dans ITSM à sa première connexion. Il faut choisir niveau, profil, groupe et entreprise ; la liste noire (Automatically create blacklist) empêche certaines comptes d'être créés seuls.
    • Test : vérifie la connexion avant d'enregistrer. En cas d'échec, le problème vient généralement du DNS, de TLS, du domaine ou des identifiants de service.

    LDAP¶

    LDAP est l'équivalent générique d'AD : un annuaire avec des utilisateurs et des groupes. Pandora ITSM prend en charge LDAPv1, LDAPv2 et LDAPv3.

    Champ Ce qu'il indique
    LDAP server Hôte ou IP LDAP
    LDAP port Port, généralement 389 ou 636
    LDAP version LDAPv1, LDAPv2 ou LDAPv3
    Start TLS Chiffre la connexion
    Base DN Point de départ de la recherche
    Login attribute Attribut contenant le nom d'utilisateur (uid, sAMAccountName, etc.)

    Comme pour AD, il existe Fallback to local authentication, Automatically create remote users et une liste noire. Le bouton Test vérifie la connexion.

    Les erreurs typiques sont un Base DN trop haut, un attribut de connexion erroné ou un certificat TLS qui ne valide pas. Si le bind échoue, l'utilisateur n'arrive même pas à vérifier son mot de passe.

    Pandora FMS¶

    Pandora ITSM peut déléguer l'authentification à un serveur Pandora FMS. C'est utile lorsque PFMS centralise déjà les utilisateurs et que vous ne voulez pas maintenir deux annuaires.

    • URL to Pandora FMS setup : l'URL complète de l'API v2, par exemple https://<host>/pandora_console/api/v2.
    • Token : le token API v2 de l'utilisateur admin de PFMS.
    • Test : vérifie que la connexion fonctionne avant d'enregistrer.

    La création automatique d'utilisateurs permet d'attribuer niveau, profil, groupe et entreprise. Choisissez toujours le moindre privilège ; une auto-création avec un profil administrateur est une porte ouverte avec un autocollant de bienvenue.

    Le mot de passe de l'utilisateur distant se gère sur le serveur PFMS. Si vous changez le mot de passe dans ITSM, vous ne changez pas celui de PFMS.

    Authentification à deux facteurs¶

    L'authentification à deux facteurs (2FA) ajoute une seconde preuve après le mot de passe. Pandora ITSM s'intègre à Google Authenticator et aux applications TOTP compatibles.

    Dans Setup → Setup → Authentication configuration → Two-factor authentication :

    • Two-factor authentication : active la fonctionnalité.
    • Force 2FA for all users : oblige les utilisateurs à la configurer.
    • Warning 2FA for all users : les avertit seulement qu'ils devraient la configurer.

    Choisissez l'une des deux options de comportement avant d'enregistrer. Si vous ne forcez ni n'avertissez, le 2FA est disponible mais personne ne le remarque.

    Chaque utilisateur l'active dans People → Edit my user :

    1. Activez Two-factor authentication.
    2. ITSM génère une clé et un QR code (Pandora ITSM: <id-user> + clé).
    3. Scannez le QR ou saisissez la clé dans l'application.
    4. Saisissez le code généré et cliquez sur Validate code.
    5. À la connexion suivante, après le mot de passe, il demande le code temporaire.

    Si un utilisateur perd son appareil, un superadministrateur peut utiliser Reset double factor authentication code. Si celui qui perd l'appareil est le superadministrateur, la réinitialisation se fait depuis sa session : ITSM envoie un courriel avec un lien valable 15 minutes. C'est pourquoi SMTP doit fonctionner et l'horloge du serveur doit être synchronisée ; une horloge décalée invalide les codes.

    Politique de mots de passe¶

    Dans Setup → Setup → Password policy setup. La politique ne s'applique pas aux superadministrateurs.

    Option Ce qu'elle fait
    Enable password policy Active les autres règles
    Min. size password Longueur minimale ; 5 par défaut
    Password must have numbers Exige au moins un chiffre
    Password must have symbols Exige au moins un symbole
    Password expiration (days) Expiration ; 0 signifie qu'elle n'expire jamais
    Force password change on first login Oblige à le changer à la connexion
    User blocked if login fails (minutes) Minutes de blocage après les tentatives échouées
    Number of failed login attempts Tentatives avant blocage

    Si la politique est active, la génération automatique de mots de passe la respecte aussi. Et si elle n'est pas active, les autres options ne font rien : l'interrupteur général commande.

    Session et options de sécurité¶

    Dans Setup → Setup → General setup, plusieurs options affectent l'accès :

    • Session timeout (secs) : durée maximale de session ; 9000 secondes par défaut.
    • Enable HTTPS access : force HTTPS dans la console.
    • Use SSL certificate et Path of SSL certificate : certificat et chemin ; /etc/ssl/certs/pandoraitsm.pem par défaut.
    • Access port : port d'accès, 80 par défaut.
    • Public access to server : URL publique ; elle doit inclure le suffixe /pandoraitsm. Mal configurée, la console peut devenir inaccessible.
    • API password : mot de passe global pour les requêtes API. Les tokens API v2 sont par utilisateur ; ne les confondez pas.
    • Login hash password : sert à générer une URL unique de pré-authentification.
    • Hide version : masque la version dans le pied de page et sur l'écran de connexion.
    • Show modal last time logged : montre à l'utilisateur la date et l'heure de son dernier accès.

    Si vous activez HTTPS, vérifiez le certificat et la chaîne de confiance. PHP peut avoir besoin du fichier de CA déclaré dans openssl.cafile. Un certificat expiré ne prévient pas dans la documentation ; le navigateur le fait.

    Problèmes fréquents¶

    Symptôme Cause probable Vérification
    Le superadministrateur n'entre pas avec AD/LDAP C'est local par conception Utilisez son mot de passe local
    Un utilisateur distant n'entre pas et son mot de passe est correct Fallback désactivé ou bind distant en échec Vérifiez la méthode et le Test
    LDAP/AD ne se connecte pas DNS, port, TLS ou Base DN Lancez le Test et consultez le journal
    L'utilisateur est créé sans profil ni groupe Auto-création incomplète Vérifiez niveau, profil, groupe et entreprise
    Le code 2FA est refusé Horloge désynchronisée Synchronisez l'heure du serveur
    Le lien de réinitialisation 2FA du superadmin n'arrive pas SMTP en panne Vérifiez la configuration du courriel
    La console ne charge pas après activation de HTTPS Certificat ou URL publique incorrects Vérifiez Apache, le certificat et access_public
    L'utilisateur est bloqué Tentatives échouées Attendez les minutes configurées ou vérifiez l'utilisateur

    Bonnes pratiques¶

    • Utilisez un annuaire central s'il existe ; ne dupliquez pas les comptes.
    • Gardez un superadministrateur local comme voie de secours.
    • Choisissez le moindre privilège dans l'auto-création des utilisateurs distants.
    • Forcez le 2FA pour les administrateurs, ne vous contentez pas de les avertir.
    • Révisez la politique de mots de passe après chaque changement d'organisation.
    • Vérifiez HTTPS et l'URL publique avant d'enregistrer.
    • Documentez quelle méthode utilise chaque collectif et qui peut la changer.
    • Testez l'accès distant et local avant de considérer la configuration terminée.
