    Authentication and security¶

    Authenticating is not filling in a form: it is proving who you are before the product lets you do anything. In Pandora ITSM that door can stay at home, be delegated to a directory or shared with Pandora FMS. Choosing the wrong method does not break the console on day one; it leaves it open or locks out someone who should be able to get in.

    The point of this chapter is simple: authentication is configured once and reviewed every time the organisation changes. A directory that no longer exists, a password policy nobody remembers and a 2FA that depends on email are very effective ways of locking yourself out of your own tool.

    How you get into Pandora ITSM¶

    Access has two layers that should not be mixed:

    • Authentication: who you are. The configured method resolves it.
    • Authorisation: what you can do. Groups and profiles in 2.1 resolve it.

    A user can authenticate correctly and have no permissions at all. Or the other way around: have a huge profile and be unable to log in because their directory is down. The first layer is here; the second is in 2.1.

    Super administrators are the exception: they always authenticate locally in Pandora ITSM, even if the rest of the users use AD, LDAP or Pandora FMS. It is a deliberate decision so that a directory failure does not leave the product without a master key.

    Authentication method¶

    Configuration is in Setup → Setup → Authentication configuration.

    Method What it uses When it makes sense
    Local Pandora ITSM Users and passwords in the database Small installations or no central directory
    LDAP Standard LDAP directory Organisations with OpenLDAP, 389 Directory Server, etc.
    Active Directory Microsoft AD Companies with accounts and groups in AD
    Pandora FMS API v2 of a PFMS server Environments that already centralise users in Pandora FMS

    Pandora ITSM checks the configured remote method first. If the user exists and the password is correct, they get in; if it fails, they can use local authentication only if fallback is enabled.

    Local authentication¶

    It is the default and the simplest option: users live in tusuario and the password is checked against the database.

    • Users are created and edited in People → User management (2.1).
    • The password policy applies here.
    • Password recovery sends an email link, so it needs working SMTP.
    • Super administrators always use this path.

    For a small installation it is enough. For an organisation with a directory, duplicating users in two places usually ends up in orphan accounts.

    Active Directory¶

    Delegating to Microsoft Active Directory centralises accounts and credentials. Pandora ITSM still needs the profile and the group: AD says who you are; ITSM decides what you can do.

    Connection fields:

    Field What it means
    Active directory server Domain controller host or IP
    Active directory port Port, usually 389 or 636
    Domain AD domain
    Start TLS Encrypts the connection with TLS

    Important options:

    • Fallback to local authentication: if AD fails, allows login with the local password. Useful as a safety net; also a door to watch.
    • Advanced Configuration AD: links AD groups to Pandora ITSM profiles and groups. This is how an AD user inherits the right profile.
    • Automatically create remote users: creates the user in ITSM the first time they log in. You must choose level, profile, group and company; the blacklist (Automatically create blacklist) prevents certain accounts from being created on their own.
    • Test: checks the connection before saving. If it fails, the problem is usually DNS, TLS, domain or service credentials.

    LDAP¶

    LDAP is the generic equivalent of AD: a directory with users and groups. Pandora ITSM supports LDAPv1, LDAPv2 and LDAPv3.

    Field What it means
    LDAP server LDAP host or IP
    LDAP port Port, usually 389 or 636
    LDAP version LDAPv1, LDAPv2 or LDAPv3
    Start TLS Encrypts the connection
    Base DN Starting point for the search
    Login attribute Attribute containing the user name (uid, sAMAccountName, etc.)

    As with AD, there are Fallback to local authentication, Automatically create remote users and a blacklist. The Test button checks the connection.

    Typical errors are a Base DN that is too high, a wrong login attribute or a TLS certificate that does not validate. If the bind fails, the user never even gets to check their password.

    Pandora FMS¶

    Pandora ITSM can delegate authentication to a Pandora FMS server. It is useful when PFMS already centralises users and you do not want to maintain two directories.

    • URL to Pandora FMS setup: the full URL to API v2, for example https://<host>/pandora_console/api/v2.
    • Token: the API v2 token of the PFMS admin user.
    • Test: checks that the connection works before saving.

    Automatic user creation lets you assign level, profile, group and company. Always choose least privilege; auto-creation with an administrator profile is an open door with a welcome sticker.

    The remote user's password is managed on the PFMS server. If you change the password in ITSM, you are not changing the PFMS one.

    Two-factor authentication¶

    Two-factor authentication (2FA) adds a second proof after the password. Pandora ITSM integrates with Google Authenticator and compatible TOTP apps.

    In Setup → Setup → Authentication configuration → Two-factor authentication:

    • Two-factor authentication: enables the feature.
    • Force 2FA for all users: requires users to configure it.
    • Warning 2FA for all users: only warns them that they should configure it.

    Choose one of the two behaviour options before saving. If you neither force nor warn, 2FA is available but nobody notices.

    Each user enables it in People → Edit my user:

    1. Enable Two-factor authentication.
    2. ITSM generates a key and a QR code (Pandora ITSM: <id-user> + key).
    3. Scan the QR or enter the key in the app.
    4. Enter the generated code and click Validate code.
    5. On the next login, after the password, it asks for the temporary code.

    If a user loses the device, a super administrator can use Reset double factor authentication code. If the one who loses the device is the super administrator, the reset is done from their session: ITSM sends an email with a link valid for 15 minutes. That is why SMTP must work and the server clock must be in sync; a clock that is off invalidates the codes.

    Password policy¶

    In Setup → Setup → Password policy setup. The policy does not apply to super administrators.

    Option What it does
    Enable password policy Enables the rest of the rules
    Min. size password Minimum length; 5 by default
    Password must have numbers Requires at least one number
    Password must have symbols Requires at least one symbol
    Password expiration (days) Expiry; 0 means it never expires
    Force password change on first login Forces a change on login
    User blocked if login fails (minutes) Minutes of blocking after failed attempts
    Number of failed login attempts Attempts before blocking

    If the policy is enabled, automatic password generation also respects it. And if it is not enabled, the other options do nothing: the main switch rules.

    Session and security options¶

    In Setup → Setup → General setup there are several options that affect access:

    • Session timeout (secs): maximum session time; 9000 seconds by default.
    • Enable HTTPS access: forces HTTPS in the console.
    • Use SSL certificate and Path of SSL certificate: certificate and path; /etc/ssl/certs/pandoraitsm.pem by default.
    • Access port: access port, 80 by default.
    • Public access to server: public URL; it must include the /pandoraitsm suffix. If configured wrongly, the console can become unreachable.
    • API password: global password for API requests. API v2 tokens are per user; do not confuse them.
    • Login hash password: used to generate a unique pre-authentication URL.
    • Hide version: hides the version in the footer and on the login screen.
    • Show modal last time logged: shows the user the date and time of their last access.

    If you enable HTTPS, check the certificate and the trust chain. PHP may need the CA file declared in openssl.cafile. An expired certificate does not warn in the documentation; the browser does.

    Common problems¶

    Symptom Likely cause Check
    The super administrator cannot log in with AD/LDAP It is local by design Use the local password
    A remote user cannot log in and the password is correct Fallback disabled or remote bind failing Check the method and the Test
    LDAP/AD does not connect DNS, port, TLS or Base DN Run the Test and check the log
    The user is created without a profile or group Incomplete auto-creation Check level, profile, group and company
    The 2FA code is rejected Clock out of sync Sync the server time
    The superadmin 2FA reset link does not arrive SMTP down Check the mail configuration
    The console does not load after enabling HTTPS Wrong certificate or public URL Check Apache, the certificate and access_public
    The user is blocked Failed attempts Wait the configured minutes or check the user

    Best practices¶

    • Use a central directory if one exists; do not duplicate accounts.
    • Keep a local super administrator as a rescue path.
    • Choose least privilege in remote user auto-creation.
    • Force 2FA for administrators, not just warn them.
    • Review the password policy after every organisational change.
    • Check HTTPS and the public URL before saving.
    • Document which method each group uses and who can change it.
    • Test both remote and local access before considering the configuration closed.
